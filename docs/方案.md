# Apifox 辅助工具：产品设计书 v1.1

版本：1.1  
日期：2026-10-30  
状态：开发设计稿，尚未实现  
适用对象：PNOS 后端开发、前端联调、接口文档维护人员  
暂定产品名：Apifox 助手

> 产品定位：从真实源码中检查和补全接口说明，再完成接口契约与 Apifox 文档之间的核对、补充和同步。
>
> 第一版交付：独立运行的本地网页工具。主要流程为“选择仓库和模块 → 扫描注释缺口 → 根据代码证据生成草稿 → 确认并补全源码注释 → 核对接口契约 → 预览并同步 Apifox → 查看报告”。

本版修正 v1.0 的核心缺口：Swagger 缺少说明时，工具不能只提示用户自行补文档，必须具备方法、入参和出参注释的检查、生成、审阅及源码回写能力。源码注释补全与响应契约补全纳入第一版必做范围，详见第 7 节。v1.0 保留为历史方案，后续开发以本版为准。

## 1. 产品作用与立项理由

### 1.1 这个工具做什么

工具首先读取用户选择的 C# 仓库、接口及相关服务、DTO 和验证代码，检查缺少或失效的注释，生成带代码依据的中文注释草稿。用户审阅后，可以将选中注释补回源码，或者先导出补丁交由开发人员处理。随后结合生成的 OpenAPI/Swagger、经确认的契约补充和 Apifox 当前内容完成文档同步。

Swagger 是框架生成的结构与描述输入之一，不是所有业务含义的唯一来源。没有 Swagger 时，也应能开始源码扫描、注释补全与契约分析；不能因 Swagger 缺少 description 就失去补全能力。

它直接回答八个问题：

1. 后端已经提供、Apifox 还没有的接口有哪些？
2. 参数、请求体、响应体、枚举和必填规则有哪些不一致？
3. 哪些字段缺少说明，哪些业务规则需要人工补充？
4. 本次同步具体会改哪些接口和共享模型，会影响哪些已有接口？
5. 同步后，Apifox 中的内容是否与本次确认的目标一致？
6. 哪些接口方法、方法参数、请求/响应字段和枚举缺少有效注释？
7. 根据真实调用链，可以补出什么说明，还有哪些含义需要业务人员确认？
8. 注释是否已回写源码、进入生成文档，并最终在 Apifox 中正确呈现？

### 1.2 当前项目中已观察到的基础

本节来自 2026-10-30 对当前仓库的只读检查，不代表线上运行验证。

| 现有基础 | 已观察到的行为 | 对产品设计的启示 |
| --- | --- | --- |
| `PNOS.API/Program.cs` | 配置 Swagger，并加载运行目录下的 XML 注释 | 用框架生成文档核对传输结构，同时用源码分析补齐描述缺口 |
| `PNOS.API/PNOS.API.csproj`、`PNOS.Data/PNOS.Data.csproj` | 已启用 XML 文档生成，抑制缺少公开成员注释的 1591 警告 | “能够编译”不代表注释完整；工具应独立检查并追踪 XML 传播 |
| `PNOS.Data/Models/APIModels/PNOSActionResult.cs` | `Data` 声明为 `object?` | 仅补 `<returns>` 不能保证生成具体 data 结构，需单独分析响应契约 |
| `docs/apifox/` | 已有多个模块的同步、修补和验证脚本 | 可以提炼共同步骤，减少每次新增一次性脚本 |
| WMS 文档同步脚本 | 按项目分页查找接口、校验更新文件、补充参数和业务说明 | 产品必须有项目配置、分页读取、写入前校验和业务说明维护 |
| 采购对账文档同步脚本 | 创建共享模型、维护引用、补充异步任务进度语义 | 同步要处理引用依赖；业务流程不能仅靠 Swagger 自动推断 |
| `.apifox/` 中的审计脚本 | 检查嵌套字段说明、模型引用、必填字段等 | 文档质量检查应进入固定流程 |

相关代码位置和复用建议见第 16 节。现有脚本作为实现参考，不直接当作稳定的公共库，也不在本次设计工作中修改它们。

### 1.3 解决的问题

| 问题 | 日常表现 | 工具提供的结果 |
| --- | --- | --- |
| 源码说明缺失 | 方法有名字但无用途说明，DTO 字段只暴露类型，Swagger 同样没有说明 | 基于方法体、调用链和验证逻辑生成可审阅注释，并补回对应声明 |
| 返回结构不具体 | 通用响应中的 data 只有 object，看不到真正的列表/对象字段 | 展示返回值来源，生成经确认的逐接口响应补充契约 |
| 结构同步遗漏 | 后端新增字段，Apifox 参数或响应仍是旧结构 | 精确到字段位置的差异清单 |
| 文档维护重复 | 每次开发都临时写查找、更新、验证脚本 | 固定操作入口和统一配置 |
| 人工内容被覆盖 | 批量导入后，业务说明、示例或调试设置变化 | 明确内容归属，预览最终内容，保留受保护设置 |
| 共享模型影响不清楚 | 只想改一个接口，实际影响其他引用接口 | 展示共享模型的全部已识别接口影响范围 |
| 同步结果难判断 | 命令返回成功，但字段、引用或说明不正确 | 写入后回读核对和逐项报告 |
| 前端交接成本高 | 前端需要重新询问这次到底改了什么 | 可分享的变更说明 Markdown/HTML |

### 1.4 产品价值如何衡量

以下是上线后要测量的目标，不是已经取得的效果：

- 减少为普通接口文档更新编写一次性脚本的次数。
- 减少“后端已改、文档未改”的交接遗漏。
- 统计所选 API、参数及输入/输出 DTO 的有效注释覆盖率，空标签不计为完成。
- 单独记录“有依据的草稿、已人工确认、已回写源码、已在生成文档出现、已同步核对”的数量。
- 记录一次文档更新的人工操作耗时，与原有方式比较。
- 每次同步都能追溯输入版本、目标项目、实际修改和核对结果。
- 相同输入在同步完成后再次检查，结构差异为零，不产生重复接口或模型。

首轮用 5 次真实文档更新记录基准，再确定耗时改善指标，不先承诺节省百分比。

## 2. 使用者、场景与产品边界

### 2.1 使用者

| 使用者 | 核心任务 |
| --- | --- |
| 后端开发 | 扫描注释缺口、审阅生成草稿并补回源码，再检查和同步接口文档 |
| 文档维护人员 | 检查缺少说明、重复接口、错误引用，整理交接文档 |
| 前端开发 | 阅读变更报告，理解参数和返回值变化；无需拥有同步权限 |

第一版按单人本机使用设计。源码写入以用户选择的工作区和明确确认的补丁为边界；Apifox 写入以账号实际权限为准。两种确认分别进行，不另建用户、角色或审批系统。

### 2.2 第一版支持的场景

- 选择仓库和模块，检查接口方法、方法参数、请求/响应类型及字段的有效注释。
- 跟踪相关服务、校验、查询/映射和返回分支，生成有证据的注释草稿。
- 审阅后将选中注释回写源码，或导出可供审查的源码补丁。
- 核对通用响应实际装入的类型，补充可证实的接口响应结构。
- 新增接口后，在指定目录创建文档。
- 修改已有接口的参数、请求体、响应体和已支持的约束。
- 维护接口说明、字段说明、请求和响应示例。
- 按模块或接口范围检查文档质量。
- 预览并同步选定的接口及必要共享模型。
- 生成检查报告、同步报告和前端交接说明。

### 2.3 第一版边界

| 纳入第一版 | 后续再考虑 |
| --- | --- |
| 本地网页工作台、项目配置、任务记录 | 云端部署、多人实时协作 |
| C# 源码扫描、有限调用链取证、XML 注释补全与回写 | 全语言支持、自动推断完整权限和状态机 |
| OpenAPI 3.0.x JSON 与已确认的源码契约补充 | Swagger 2、OpenAPI 3.1、YAML 的完整支持 |
| 基于证据的语义草稿生成、人工确认和有限格式补丁 | 自动修改业务逻辑、自动重构 DTO 或返回封装 |
| 比对、补充说明、选择同步、回读核对 | 无人审阅地改源码并发布文档 |
| 已有项目、已有分支、已有目录 | 自动建项目、建分支、合并分支、批量整理目录 |
| 新建/更新接口及必要模型 | 自动删除接口、独立模型或自动移动目录 |
| 生成请求/响应示例草稿 | 创建、修改或运行 Apifox 测试用例 |
| 手工选择模块或路径范围 | Git diff 自动精确映射接口影响范围 |
| 本地快照和恢复参考信息 | 跨资源事务、自动回滚 |

工具分别报告源码注释状态、生成文档状态和 Apifox 状态。同步成功表示文档写入和核对成功，不表示业务接口经过实际调用验证。第一版不调用 PNOS 登录、导入、计费等业务接口，不读写业务数据库，不因补注释修改方法签名、校验属性或业务执行语句。

## 3. 产品形态与使用流程

### 3.1 交付形态

- 独立 Windows 本地工具，启动后打开默认浏览器。
- 使用中文界面；用户通过表单、差异列表和预览完成操作。
- 本地进程读取选定仓库，定位 API 与 DTO 符号和相关实现，生成注释草稿与补丁；随后读取 Swagger，并通过 Apifox CLI 访问 Apifox。
- 配置和任务资料保存在本机，无需额外部署数据库或云服务。
- 第一版复用已安装 CLI 的登录态；不在网页中收集 Apifox 令牌。
- 注释草稿生成可使用用户显式配置的语义模型服务；未配置时仍可完成扫描、证据整理、手工补全和补丁导出，不能将只有空模板的状态称为“已自动补全”。

启动程序名暂定 `ApifoxHelper.exe`，是拟定的交付方式，目前没有该程序。

### 3.2 首次配置

1. 启动工具，进入“项目设置”。
2. 检查 Apifox CLI 是否可用、版本是否符合已验证的兼容要求。
3. 如果尚未登录，按页面说明在本机终端完成 CLI 登录，再点击“重新检查”。
4. 选择有权限访问的 Apifox 项目和已有分支。界面持续显示项目名称、ID 和分支。
5. 选择本地仓库及 API 项目文件，配置源码允许写入范围；添加 Swagger 文件或 JSON 地址，可在完成注释补全后再添加。
6. 配置常用模块的路径范围、新接口目标目录，以及新接口所需的服务和鉴权模板。
7. 点击“保存并检查”，分别验证源码读取、符号分析、Swagger 和 Apifox 读取能力。缺少 Swagger 不阻止源码阶段；读取成功不代表源码或远端已获写入确认。

配置里要区分 Apifox 项目 ID、Apifox 分支和 PNOS 业务项目上下文。它们是不同概念，不能共用一个“项目 ID”字段。

### 3.3 日常使用：更新一个模块

1. 选择仓库、API 项目和模块，新建任务；工具记录当前工作区文件指纹，包含尚未提交的修改。
2. 点击“扫描注释”，查看方法、参数和输入/输出字段的缺失、空标签、过时说明及调用链证据。
3. 点击“生成注释草稿”，逐项查看草稿、代码依据、分析范围与待确认问题；修正并确认选中内容。
4. 预览源码差异，点击“确认应用注释”；也可以仅导出补丁。此步骤不执行 Apifox 写入。
5. 由开发人员按现有流程生成对应的 XML/Swagger，工具重新读取并检查说明传播。默认不自动 build、restore 或启动业务服务。
6. 对 `data=object` 等问题，确认逐接口响应补充契约；无法确定的返回分支保留为阻断项。
7. 查看 Apifox 差异、人工说明合并结果和共享模型影响，选择同步范围。
8. 查看最终内容与写入清单，确认同步，工具执行写入并回读核对。
9. 下载包含源码、生成文档和远端文档三阶段状态的报告，交给前端或测试人员。

第 9 步由用户自行发送，工具第一版不连接消息平台。

如果暂时无法重新生成 Swagger，可以用已确认的说明补充层构造本次文档预览，并对既有、已明确映射的接口执行说明更新；未能验证的结构修改不能由旧 Swagger 或模型猜测顶替。报告持续标记“源码已补全，生成文档未验证”，不能宣称全链路完成。

### 3.4 只检查，不同步

用户可以只扫描并导出报告，或者只导出注释补丁，不修改源码或 Apifox；也可以只完成注释回写，稍后再同步文档。源码应用和远端同步是两个独立动作。

没有在线访问条件时，可以导入两份 OpenAPI JSON 离线比较；此模式只能检查结构，无法证明 Apifox 原生设置、重复接口及当前线上状态完整，页面必须显示“离线检查”，同步按钮禁用。

### 3.5 一个具体例子

以下是假设场景，用于解释产品行为，不表示这些变更尚未在当前系统完成：

后端为 `GET /api/finance/BillList` 增加 `ArchiveId` 参数。检查后页面展示：

| 检查项 | 展示结果 |
| --- | --- |
| 参数变化 | Query 新增 `ArchiveId`，整数，是否必填以输入契约为准 |
| 文档质量 | 新参数缺少业务说明，提示补充 |
| 业务规则 | 用户填写“与 ClientId 互斥；使用场景和取值来源……” |
| 既有配置 | 保留已有接口 ID、目录、服务、鉴权和脚本 |
| 最终预览 | 显示新增参数及合并后的说明，列出本次会修改的内容 |
| 同步结果 | 回读参数、说明及受保护设置；一致才标记为核对通过 |

“与 ClientId 互斥”必须来自人工确认的规则或已有文档，不能从两个字段同时存在推断出来。

## 4. 页面设计

第一版采用一个工作台，包含“项目设置、检查任务、任务详情、历史报告”四个主要入口。任务详情内部完成差异查看、说明编辑和同步预览，避免拆成过多页面。

任务详情新增“源码注释”页签，默认先展示注释缺口和已生成草稿，再进入“生成文档”和“Apifox 差异”页签。

### 4.1 项目设置

| 字段/区域 | 说明 |
| --- | --- |
| 配置名称 | 例如“PNOS 开发文档” |
| CLI 状态 | 可执行入口、版本、登录状态、兼容性检查结果 |
| Apifox 项目/分支 | 从可访问资源中选择；保存明确 ID 和分支标识 |
| 代码工作区 | 仓库路径、API 项目、依赖项目、允许读取/注释回写的范围 |
| 分析能力 | 语法解析状态、语义符号解析状态、未解析依赖和条件编译配置 |
| 草稿生成 | 所用生成方式、模型配置状态、代码材料发送范围；凭据不显示或导出 |
| Swagger 来源 | 文件或 JSON URL；源码阶段可为空，不接受 Swagger UI 页面地址 |
| 来源版本备注 | 用户填写提交号、构建号或版本描述，可为空但显示“未绑定代码版本” |
| 模块范围 | 模块名与路径前缀映射，例如“财务”→`/api/finance/` |
| 新接口目标 | 已有目录、服务、明确选择的鉴权/公共参数模板 |
| 操作 | 检查连接、保存、导出不含凭据的配置 |

新接口模板只复制明确列出的配置字段，不克隆任意接口的脚本、用例、Mock 或历史请求。

### 4.2 检查任务列表

每项显示任务名称、项目/分支、来源备注、创建时间、状态、变化接口数和未处理项数。

操作：新建检查、扫描注释、查看结果、导出补丁/报告、基于相同配置重新检查。列表同时显示源码注释、Swagger 传播和 Apifox 同步的分阶段状态，不能用一个绿色“完成”掩盖后续未验证。

### 4.3 任务详情：差异工作台

```text
Apifox 助手    PNOS / 指定分支    来源：本地 Swagger    版本备注：...

任务：财务接口文档更新
新增 2   结构变化 3   说明变化 1   冲突 1   无变化 20

[模块] [变化类型] [风险] [关键词]             [导出检查报告]

接口列表                      差异详情
☐ GET  /api/finance/...        变化摘要 | 字段对比 | 业务说明 | 最终预览
☐ POST /api/finance/...        位置：query.ArchiveId
                              Apifox：不存在
                              目标：integer / optional
                              来源：Swagger
                              说明：[填写业务用途...]

共享模型影响：模型 X → 选中接口 2 个，范围外接口 3 个
待处理：1 个冲突，2 项业务说明需要确认

已选择 2 个接口，将涉及 1 个模型              [生成同步预览]
```

关键交互：

- 初次进入时同步项默认不勾选。
- 差异详情显示旧值、新值、字段位置、来源和风险原因，不能只有两个大段 JSON。
- 删除字段、类型变化等高风险项必须逐项确认，不能被“选择普通变化”批量带入。
- 用户可以编辑说明和示例；结构来自生成契约及已证实、经确认的补充，不能在普通文字编辑框随意改类型。
- 注释草稿旁必须展示符号、源文件/行号、支持该描述的代码片段、分析覆盖范围和待确认问题。回写位置是对应 C# 声明，不只是 Apifox description。
- 响应契约补充使用单独页签，明确区分框架生成结构、代码证实结构和未证实猜测；存在冲突时阻断相关结构同步。
- 生成目标示例时使用虚构值或变量占位；示例须通过当前支持范围内的结构校验后才能提交。
- 未填写的业务说明留在本地待办，不把“待确认”等草稿文字发布到 Apifox。
- 同一接口默认作为一个结构同步单元；不开放任意叶子字段拼装，避免产生不完整契约。

### 4.4 同步预览

必须展示：目标项目和分支、接口创建/更新清单、模型清单、共享模型影响、说明改动、保留设置、校验结果及未支持内容。

主按钮为“确认同步 N 个接口、M 个模型”。确认绑定当前计划版本；说明、选择或目标变化后，原确认失效，需要重新预览。

如果只有文档说明缺失，可由用户明确选择“保留现状，本次不补充”；报告保留未完成事项。未解析引用、重复身份、未识别的写入结构等阻断项不能跳过。

### 4.5 结果与历史报告

源码区域显示“已生成待审阅、已确认、补丁已导出、已回写、源码冲突、生成文档未验证”。Apifox 区域逐项显示“已写入并核对、写入结果待确认、核对失败、冲突、未执行、无需修改”。

报告包括实际写入的接口链接、未完成原因、来源版本和未验证范围。接口链接须使用平台返回或验证过的链接格式，不能自行猜测链接后宣称可用。

提供“重新核对”和“生成后续任务”；第一版没有无条件重放写入或一键回滚按钮。

## 6. 比对规则与判断依据

### 6.1 数据来源和优先级

| 内容 | 默认依据 | 冲突处理 |
| --- | --- | --- |
| 方法、路径、参数位置、类型、必填、约束、请求/响应结构 | 框架生成 Swagger + 有代码依据且经确认的契约补充 | 两者矛盾时阻断；不能用语义猜测覆盖框架绑定/序列化行为 |
| API、入参和出参语义草稿 | 选中工作区的符号、实现、验证、映射和返回分支 | 有依据生成候选，含义不明转为待确认，不默认提交 |
| 已有接口标题、目录、标签、服务、鉴权、公共参数 | Apifox 当前内容 | 第一版保留；Swagger 相关变化仅列待确认 |
| 已有业务说明、字段说明、请求/响应示例 | Apifox 当前内容 | 同一语义位置保留；结构变化影响说明时提示复核 |
| 用户明确编辑/确认的源码注释、说明和示例 | 当前任务中确认的补充内容 | 覆盖范围须精确到对应符号/文档位置，并分别进入源码和远端预览 |
| 新接口所需目录、服务和鉴权 | 项目中明确选择的模板 | 无模板或无法确认时阻断创建，不随意复制其他接口 |
| 脚本、Mock、用例、环境变量、鉴权密钥 | Apifox 原生配置 | 不作为同步目标；更新时保留并核验可读取的相关设置 |

Swagger 未声明鉴权，不代表业务允许匿名；不能据此清空已有鉴权。业务权限、互斥参数、进度状态和幂等规则可以从完整可定位的代码路径提出候选，但必须显示依据并经人工确认；分析中断或未读到某个校验不代表不存在校验。

### 6.2 接口与模型身份

- 接口身份为“Apifox 项目 + 分支 + HTTP 方法 + 精确路径”。方法统一大写，路径保留大小写、尾斜线和参数名。
- 不把接口标题或 `operationId` 当作唯一身份；不自动合并 `/a/{id}` 与 `/a/{key}`。
- 路径或方法变化按“新增 + 旧资源未匹配”展示。第一版不自动改名或删除旧接口。
- Apifox 同一身份出现多个接口时，阻断该身份同步并列出候选，不能取第一条覆盖。
- 模型采用显式映射；首次可按完全同名生成候选，唯一且经用户确认后保存“源模型键 → 远端模型 ID”。
- 模型名称相近、大小写不同或候选不唯一时不自动绑定。
- 远端 ID 是平台身份，不能用随机生成 ID 替换已有资源 ID。

### 6.3 第一版比较范围

| 范围 | 比较内容 |
| --- | --- |
| 参数 | path/query/header/cookie、名称、必填、类型、格式、枚举、默认值、已支持约束 |
| 请求体 | required、媒体类型、JSON 结构；multipart 文件字段和支持的普通字段 |
| 响应 | HTTP 状态码、媒体类型、响应头、结构、nullable、数组和嵌套属性 |
| 模型 | properties、required、items、additionalProperties、支持的校验约束和引用 |
| 文档 | 标题、说明、字段说明、示例的有无及用户明确编辑的差异 |
| 保留项 | 目录、服务、鉴权、公共参数、可读取的脚本关联和既有示例等 |

必须区分 HTTP 响应码与 `PNOSActionResult.statusCode` 业务状态。工具不以 HTTP 200 自动判断业务成功，也不把异步任务“已受理”描述成“已完成”。

### 6.4 风险分级

| 等级 | 示例 | 页面行为 |
| --- | --- | --- |
| 普通 | 新增可选请求参数、补充说明 | 可选择同步，仍需查看最终预览 |
| 潜在不兼容 | 新增必填请求参数、删除响应字段、改变类型、收紧范围 | 展示原因，逐项确认 |
| 需人工判断 | 响应枚举新增、组合结构变化、未识别格式或业务语义变化 | 不承诺兼容，要求人工处理或排除 |
| 阻断 | 悬空引用、重复身份、冲突未解决、目标发生变化 | 禁用相关同步动作 |

风险判断区分请求和响应方向。例如请求允许值减少通常更严格，响应新增枚举值可能影响前端穷举处理；不能套用同一个“枚举增加=兼容”规则。

### 6.5 标准化与引用

- 消除纯对象键顺序、可作为集合处理的 `required` 等造成的假差异；不随意重排全部数组。
- `enum` 按值及类型比较；数字 `1` 与字符串 `"1"` 不能视为相同。
- 显式区分“不存在”“null”“空数组”“空对象”，不统一丢弃。
- 本地 `components/schemas` 与 Apifox 原生模型 ID 先映射为逻辑引用再比较，不能直接比较引用字符串。
- 通过引用图遍历，使用已访问集合处理递归模型，不把所有模型无限展开。
- `allOf/oneOf/anyOf` 保留其组合语义；第一版不做复杂等价推理，无法可靠转换的写入标为不支持。
- 第一版只自动处理文档内引用；外部 URL/文件引用提示不支持并阻断相关同步。
- 未知扩展原样保留在已有远端资源中；若源结构包含可能改变验证/序列化语义且尚未支持的部分，不能忽略后同步。

## 7. 源码注释补全与业务说明保护

### 7.1 业务说明编辑模板

每个接口可维护以下内容；不是所有接口都必须填满模板。

| 区域 | 内容举例 |
| --- | --- |
| 使用场景 | 哪个页面、哪个操作调用 |
| 前置条件 | 所需档案、配置或业务状态 |
| 项目与权限 | 项目上下文的来源、允许操作的范围 |
| 参数规则 | 参数取值来源、互斥、依赖、默认业务含义 |
| 操作结果 | 成功、失败、部分完成或已受理的含义 |
| 异步后续 | taskId 来源、轮询接口、完成/失败条件 |
| 示例 | 虚构请求、响应和必要说明 |

模板用于组织说明；自动补全部分必须读取相关代码并生成有依据的中文草稿，不能停留在空模板或把 Name 翻译成“名称”。第一版纳入可配置的语义模型辅助生成能力，模型只能提交注释候选和证据引用，最终内容须经用户审阅。未配置模型时保留扫描和手工补全能力。

### 7.2 合并规则

1. 已有接口说明默认保留；用户可以明确编辑完整说明，提交前查看全文差异。
2. 字段说明按接口、请求/响应位置和属性路径定位；仅保留仍存在且能准确对应的字段说明。
3. 字段被移除时，其说明不拼接到别处；报告列出移除影响。
4. 字段类型或约束变化时，已有说明和示例标为需要复核；原有示例若不符合新结构，不自动发布为有效示例。
5. 未进行人工编辑时，不能用空值或 Swagger 缺省值覆盖已有人工说明。
6. 已有示例在更新后仍需保留；用户明确替换的示例才作为本次目标。新增示例与原生用例是不同资源。

### 7.3 首次使用与后续使用

首次没有历史基线时，只能确认“源和 Apifox 当前不一致”，不能断言哪一方是最近修改。所有写入项均需用户选择和确认。

同步核对通过后，为成功资源保存源结构、已确认补充内容和远端结果的基线。后续检查若源与远端都改变同一受管理部分，标记冲突；只有单侧改变时可以提出合并建议，但仍由当前计划确认。

说明编辑以本次读取的远端内容为基础，不把旧基线中的人工文字强行覆盖回去。基线不能替代应用前的目标重读。

### 7.4 注释补全的最小范围

只扫描所选 API 及其实际关联类型，不要求先补完整仓库。

| 对象 | 需要检查和补全的内容 | 写入位置 |
| --- | --- | --- |
| Controller/接口方法 | 用途、操作对象、重要前置条件、结果和异步状态含义 | 方法 XML `summary`、`remarks`、`returns` |
| 方法入参 | 业务含义、取值来源、是否可省略及可证实的默认规则 | 与真实参数名对应的 `param` |
| 请求 DTO | 类型用途、字段含义、单位、范围、枚举和字段依赖 | 对应类型/属性 XML 注释 |
| 响应 DTO | 返回对象用途、字段业务含义、单位、空值和集合含义 | 对应类型/属性 XML 注释 |
| 枚举 | 类型用途、每个值的含义和适用范围 | 枚举及成员 XML 注释 |
| 相关服务/接口 | 能帮助解释 API 的实际行为；已有实现注释与接口注释冲突 | 读取取证；仅在用户选中时回写，不扩展成全库注释改造 |

方法参数是 DTO 时，给 `request` 写一个 `<param>` 不能替代 DTO 字段说明。响应是列表或分页对象时，应继续检查元素类型与容器字段；`Task<T>` 的返回说明描述完成后的业务结果，而不是简单写“异步任务”。

检查还要覆盖：空标签、参数改名后未更新的标签、注释与当前校验冲突、继承/接口注释能否真正进入生成链路。已有注释并不自动视为业务事实，冲突需要展示双方依据。

### 7.5 如何从没有注释的代码生成有用草稿

分析按选中接口展开：

```text
Controller 方法、路由/绑定特性
    → 实际调用的服务接口及可确定实现
    → 请求验证、状态检查、项目/权限检查
    → 查询过滤、写入/更新、字段映射、返回分支
    → 请求 DTO、返回 DTO、枚举和相关测试/已确认说明
    → 中文候选注释 + 代码证据 + 未解决问题
```

- 结构信息使用 C# 语法树和符号关系提取，避免正则匹配同名方法造成误绑定。
- 限定分析预算并记录已读/未读调用；动态派发、多实现 DI、反射、外部程序集等不能唯一解析时显示缺口，不伪造完整调用链。
- 明确“类型允许 null”“框架要求字段”“业务条件必填”的区别。可空类型、初始化值和数据库列类型不能单独证明业务默认值、计量单位或权限。
- 从执行的条件与分支总结可证实规则，例如 `amount < 0` 的拒绝条件；条件必填应保留触发条件，不能变成所有请求都必填。
- 调用方、字段投影和配置可以协助解释含义；测试与历史说明作为辅助证据，不能覆盖当前生产代码的冲突事实。
- 每条草稿关联证据编号，证据包含文件、符号标识、代码位置、片段指纹和覆盖范围。模型输出的证据编号必须能在本次材料中找到。
- 共享 DTO 的属性注释只写可复用的字段含义。仅在某个接口、业务条件下成立的规则放到该接口的 remarks 或逐接口补充中，不能写成整个共享类型的无条件规则。
- 展示“代码可证实、人工已确认、需业务确认、分析未覆盖”等状态，不使用无法校准的百分比分数冒充正确率。
- 不在源码注释中写推测为事实；没有证据的业务含义以问题留在任务中，用户补答后才可确认。

一个合格输出不仅是注释文字，还应显示“这段规则来自哪个判断/映射”“返回对象来自哪个表达式”“还有哪条分支没读清楚”。模型不得直接执行命令、修改文件或调用 Apifox，所有修改通过本工具的受限应用流程。

### 7.6 注释示例与审阅界面

以下为假设示例，规则由示例代码中的真实条件证实后才可采用，不代表当前项目中存在同名接口。

```csharp
/// <summary>
/// 分页查询指定计费客户的月度费用明细。
/// </summary>
/// <param name="billingClientId">计费客户 ID，必须大于 0。</param>
/// <param name="billPeriod">账期，格式为 yyyy-MM。</param>
/// <returns>包含明细列表与分页信息的业务响应。</returns>
/// <remarks>仅返回当前账号可操作项目内的数据。</remarks>
public Task<PNOSActionResult> GetFeeDetails(int billingClientId, string billPeriod)
```

上述草稿中的“大于 0”“yyyy-MM”“权限范围”均须分别对应已定位的校验或查询过滤证据；只有参数名时不能生成这些结论。示例中的方法签名只用于解释，补丁不会重新生成方法声明。

源码注释页签提供：缺口列表、源代码与证据、候选注释、问题填写区、源码差异预览。用户可接受、编辑或暂缓每条候选；支持批量接受已经逐条审阅的项，不默认接受未经审阅的业务语义。

### 7.7 安全地将注释补回源码

1. 以工作区当前文件为基准，记录原文件指纹、编码/BOM、换行及符号定位；基准包含已有未提交修改。
2. 生成仅包含 XML 文档注释改动的补丁，展示路径、符号、旧注释和新注释。
3. 用户确认本次源码补丁后，应用前重新核对目标文件及所依赖证据片段指纹；变化则要求重新分析。
4. 应用器只能操作选中声明的文档注释，正确转义 XML 特殊字符，不接受模型返回的任意 C# 代码块或命令。
5. 保留原缩进、BOM、CRLF/LF 和其他内容；不调用全文件 formatter，不更改属性特性、执行语句、参数名或签名。
6. 静态比较改前改后的语法 token 与预处理指令，确认执行代码、字面量和编译条件完全不变；解析注释 XML，检查 param 名称和 cref 解析情况。
7. 写入前保存选中文件的前态，逐文件原子替换并记录状态。多文件中途失败时如实显示部分完成，不自动回滚或覆盖后来修改。
8. 可选择仅导出 `.patch` 和说明，不直接写工作区。导出不代表已应用，更不代表 Swagger 已更新。

默认只补缺少或空的有效标签。对已有有效注释的改写、移除或与源码矛盾的修正必须明确展示，不整段覆盖人工内容。工作区允许范围之外、生成代码、外部包及定位不明确的符号不自动修改。

### 7.8 返回值契约补全：注释之外的独立能力

当前项目的 `PNOSActionResult.Data` 是 `object?`。例如本次检查到 `WmsBillingClientList` 将 `GetWmsBillingClientsAsync` 的结果装入响应，而服务接口返回 `Task<List<WmsBillingClientResponse>>`。这说明可以沿返回表达式追踪实际 data 类型，但还必须检查其他返回/错误分支，不能只依据方法名称。

产品需要完成以下步骤：

- 识别实际 `return` 表达式、封装构造函数、赋值及被调用方法返回类型，收集本次接口不同分支的候选形状。
- 跟踪对象、集合和分页类型的字段，并使用当前项目的序列化名称、忽略规则和已知转换器信息核对对外字段。
- 为简单、明确的返回形状生成逐接口 `responseContract.json`：接口身份、HTTP/业务分支、data 类型引用、可空情况、证据、确认状态及源码指纹。
- 经审阅的响应补充只增强该接口的文档，不把共享 `PNOSActionResult.data` 全局改为某一个 DTO。
- 动态对象、匿名返回、多个形状、自定义转换器或条件无法覆盖时，列出未解析点；首版不可靠支持的情况保留人工确认或阻断，不能当成已完整补全。
- 不通过默认增加泛型包装、修改返回签名、创建业务 DTO 或随意添加特性解决文档问题。确需调整文档元数据时提出单独建议，不混入“仅注释补丁”。

补 `<returns>` 能说明业务含义，但不会自动把 object 变成具体类型元数据；`<param name="request">` 也不会自动补齐请求对象所有字段。接口结构与文字说明分别验收。

### 7.9 从源码到 Swagger 再到 Apifox 的传播核对

已确认草稿转成统一说明条目，记录“C# 符号/参数或属性 → 接口身份 → 请求/响应位置 → 对外 JSON 名称”的映射。相同条目用于生成源码补丁、核对 Swagger 和形成 Apifox 补充计划，避免三处重新手填导致含义漂移。映射不唯一时列出所有使用位置供确认；与现有远端人工说明矛盾时展示冲突，不因默认保留远端内容就静默丢弃已确认的源码说明。

分别检查四个结果：

1. 已确认注释是否准确写到目标符号，当前代码和证据是否仍匹配。
2. 所属项目是否生成 XML 文档，实际产物中的成员条目是否包含选中注释；不能仅看 csproj 开关。
3. Swagger 是否读取这些 XML，summary、参数和属性说明是否出现在正确位置；不同标签的实际呈现以当前生成器验证为准。
4. Apifox 是否保留了确认后的说明与具体输入/输出契约。

若注释已写入但构建产物/运行服务仍旧，显示“源码已完成，Swagger 待刷新”。工具提供适当的定向生成操作说明，默认不自动构建、恢复依赖或重启服务；用户明确选择执行时，才运行预览过的最小开发环境操作，记录实际结果。

若只应用了说明/响应补充层而未完成生成物传播，报告显示“本次 Apifox 已补充，生成链路尚未闭合”，后续刷新 Swagger 时必须继续保留已确认补充，不以旧结构覆盖。

### 7.10 模型辅助生成的配置边界

首版允许配置一种实际可用的语义生成服务，或通过清晰定义的材料/结果文件交给现有编码助手处理。两种入口使用同一候选格式：符号、建议标签和文字、证据编号、待确认问题、已覆盖范围；无返回结果时不能标记生成成功。

模型只接收用户已选模块及必要上下文；本地扫描和读取源码不自动授权向外部服务发送整个仓库。启用外部生成前展示材料范围，排除配置密钥、连接串和无关文件；凭据使用本机受保护存储，不进入任务报告或导出包。不强制绑定某一家模型厂商，也不要求先接入模型才能开始本地检查。

实现时必须包含一种经验证可产出真实候选的生成链路；仅做缺口列表和空白编辑框不满足 F14，也不能通过首版验收。

## 8. 同步规则、失败处理与恢复

### 8.1 同步前的必要条件

- 采用源码分析结果时，相关符号、证据与补充契约指纹仍有效，所选语义内容已审阅，不能使用旧代码上的生成结论。
- 项目、分支、源快照和模型映射明确。
- 所选接口及必要依赖全部可解析。
- 首次绑定、潜在不兼容变化、业务内容复核已完成。
- 同步计划及写入文件通过本工具校验和当前 CLI Schema 校验。
- 写入前快照与执行意图日志已成功保存；本地存储失败不能继续写入。
- 在开始执行和每个资源写入前重读相关目标，检查指纹与计划一致。
- 应用前重新计算源文件指纹；URL 来源重新读取并核对。来源变化后计划过期，需重新检查。

当前任务使用冻结的输入快照，不在执行中静默混入新的源内容。

源码补丁与 Apifox 同步使用不同计划和确认。注释回写后，源文件指纹变化，应记录新的源码阶段快照，重新生成文档预览；不能沿用回写前的远端同步计划。仅格式上的注释变化与业务证据变化分别记录，避免把无关注释变化误判成业务事实已改变，也避免忽略实际条件或类型变化。

### 8.2 共享模型影响控制

修改已有共享模型前，读取当前分支全部接口和模型的必要引用信息，计算直接和间接引用。不能只查当前选中模块。

- 页面同时列出范围内、范围外受影响接口。
- 范围外影响必须在预览中明确确认；无法确认时可排除该模型及依赖更新。
- 全部必要分页/详情读取未完成时，阻断该模型变更；不把“没读取到”当作“没人引用”。
- 未选择的接口不单独改写，但引用共享模型后文档表现可能变化，报告必须如实说明。
- 第一版不完整分析用例脚本等任意文本里的模型依赖，这部分列为人工复核范围。

新增模型按依赖顺序创建，再更新引用它们的接口。新建互相递归引用模型若需要预建空壳等额外步骤，第一版阻断并要求人工准备；已有递归模型在映射完整且可表示时可以比对和更新。

### 8.3 执行方式

首版按资源顺序执行，避免同时写同一目标。

1. 校验计划和源版本。
2. 获取同一项目/分支的本地执行锁。
3. 再次确认目标当前内容未变，并保存前态快照。
4. 按依赖顺序处理模型，再处理接口。
5. 每个资源写入后立即回读，核对受管理内容及应保留设置。
6. 保存逐项结果。首次写入错误、结果不确定或核对失败后停止后续写入。
7. 仅对已核对通过的资源推进基线，最后生成报告。

确认粒度是同步计划，不需要每个正常资源再次弹窗；计划变化才要求重新确认。

### 8.4 状态定义

| 状态 | 含义 |
| --- | --- |
| 源码扫描中 | 正在定位符号、注释缺口和相关实现，没有写文件 |
| 注释待审阅 | 草稿和依据已生成，还有需要用户确认或补答的内容 |
| 注释待应用 | 源码补丁已预览，尚未写入工作区 |
| 生成文档待核对 | 注释已回写，或补丁已由用户应用，但 XML/Swagger 的传播尚未验证 |
| 检查中 | 正在读取和计算，没有远端修改 |
| 待处理 | 有冲突、阻断或需要确认的内容 |
| 可预览 | 已能生成可审阅计划 |
| 待确认 | 计划已冻结，等待用户确认 |
| 执行中 | 已开始写入，部分资源可能已生效 |
| 已核对通过 | 所有计划内动作均回读一致 |
| 部分完成 | 至少一个资源核对通过，其他动作未完成 |
| 失败 | 无已核对通过动作，且存在失败或未知结果；不代表远端一定未改变 |
| 已过期 | 源、目标或计划版本变化，需要重新检查 |
| 已取消 | 用户在写入前取消，或执行中请求在当前动作结束后停止；保留已发生结果 |

资源级状态至少包括：待执行、已写入待核对、已核对通过、写入失败、结果待确认、核对失败、冲突、未执行、无需修改。任务另外保存源码、生成物、远端三个阶段的结果；“远端已核对通过”不能覆盖仍未完成的源码/生成物状态。

### 8.5 超时、重试与重复创建

- 读取操作可有限重试；建议最多 3 次，并遵守平台限流信息。
- 写入超时不能直接重发，先标记“结果待确认”，按 ID 或接口身份回读当前状态。
- 创建动作前复查同身份资源；已有且目标一致时记为无需修改，已有但不一致时重新生成更新计划。
- 创建后未取得 ID 时，重新查询候选；只有唯一且可核对一致时才能完成绑定，否则停止。
- 程序崩溃重启后先核对日志中未结束的动作，不能直接重放。
- 重新处理失败项时生成后续计划，成功项先检查是否已达目标，不反复创建。

本地锁不能阻止其他用户同时操作 Apifox。若平台能力探测未确认原子条件更新，执行前指纹检查仍有竞态窗口；界面提醒同步期间避免修改相同资源，产品不承诺跨客户端原子性。

### 8.6 保护与恢复边界

- 首版不自动删除接口、独立模型、目录、用例或脚本。
- 对已选资源内的字段删除属于结构更新，必须显示并确认；不与“删除远端资源”混为一谈。
- 更新使用当前远端资源作为基础，仅修改计划允许的部分。若 CLI 对嵌套对象采用替换语义，需要构造完整嵌套对象以保留其他项。
- 如果 CLI 更新会重置受保护设置且无法可靠保留，相关写入能力不能开放。
- 没有跨资源事务；模型写入成功而接口失败时，模型可能已生效，应显示部分完成。
- 第一版保存可用于排查和人工恢复的前后快照，提供平台历史记录恢复指引，不承诺快照可无损一键导回。
- 恢复操作须重新核对当前状态，不能覆盖同步后其他人的修改。

## 10. 技术落地方案

### 10.1 推荐实现

建议使用独立 .NET 8 应用，提供本地 HTTP 接口并承载静态网页。界面可先采用普通 HTML/CSS/JavaScript，保持单进程运行，不要求另建前端服务。

```text
浏览器中的中文工作台
           |
本地 .NET 8 应用（仅监听回环地址）
   |                   |                   |
源码/符号/证据分析    注释草稿与补丁       OpenAPI及契约补充
   |                   |                   |
选定仓库          本机审阅与确认        比对/计划/报告
                       |                   |
                  受限注释应用器       Apifox CLI 调用
                                           |
                                    Apifox项目及分支
```

选择这一方案是为了沿用现有 .NET 开发经验，同时让工具独立于 PNOS API、数据库及发布流程。具体 UI 框架可以在实现时按团队已有基础决定，不影响本文的行为要求。

### 10.2 最小职责划分

建议保持清晰职责：源码与符号分析、证据和候选生成、注释应用、契约比对、Apifox 调用、同步与报告。先用普通类和函数实现，不预设插件系统、策略层或通用工作流引擎。

C# 符号分析使用 Roslyn，处理重载、partial、继承、接口实现、泛型和类型引用。语法树可以在无 Swagger 时建立缺口清单；完整语义需要实际项目的引用、条件编译和生成源码信息。语义信息缺失时明确降级，不能按同名猜实现。Roslyn 的语义模型用于定位符号和表达式类型，并不自动理解所有业务规则。[Roslyn 语义模型说明](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/work-with-semantics)

加载项目配置不得隐式 restore、build 或运行自定义任务；如某种项目加载方式会执行 MSBuild targets，需在能力探测中识别，不能把它包装成无副作用的普通文件扫描。无法安全、完整加载时先提供语法扫描和缺失依赖说明。

注释回写采用受限语法位置编辑，标签与参数名遵循 C# XML 文档规则；对 `<inheritdoc>`、`cref` 和 partial 的生成行为进行专项验证，不假设 IDE 显示的说明一定已进入 XML/Swagger。[C# XML 文档标签](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/xmldoc/recommended-tags)

补充响应元数据与注释文字是不同职责。框架返回类型和相关元数据影响生成的响应描述；本工具不默认添加或更改这些特性，应先通过逐接口补充契约形成可审阅结果。[ASP.NET Core 返回类型说明](https://learn.microsoft.com/en-us/aspnet/core/web-api/action-return-types?view=aspnetcore-8.0)

Apifox 调用集中在一个边界，负责明确传递项目和分支、分页、超时、结果解析、错误脱敏以及当前 CLI 版本兼容。避免在不同页面各自拼命令。

### 10.3 本地接口草案

以下是本工具拟定接口，不是 PNOS 或 Apifox 已有接口。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/capabilities` | 当前 CLI、登录和功能兼容情况 |
| `GET/POST /api/profiles` | 查询/创建项目配置 |
| `PUT /api/profiles/{id}` | 修改配置 |
| `POST /api/tasks` | 根据配置快照创建检查任务 |
| `POST /api/tasks/{id}/source-scan` | 扫描源码、提取符号并生成注释缺口和证据 |
| `POST /api/tasks/{id}/comment-drafts` | 根据已选范围生成候选，不修改源码或调用业务接口 |
| `PUT /api/tasks/{id}/comment-drafts/{draftId}` | 保存人工修订、问题回答和审阅状态 |
| `POST /api/tasks/{id}/comment-plan` | 生成并冻结仅注释补丁 |
| `POST /api/comment-plans/{id}/apply` | 提交明确计划指纹后回写已确认注释 |
| `GET /api/comment-plans/{id}/patch` | 仅导出补丁，不写源码 |
| `PUT /api/tasks/{id}/response-contract` | 保存确认后的逐接口出参补充 |
| `POST /api/tasks/{id}/propagation-check` | 检查源码、生成 XML/Swagger 的说明对应情况 |
| `GET /api/tasks/{id}` | 查询任务摘要、进度和状态 |
| `GET /api/tasks/{id}/diffs` | 按风险和资源筛选差异 |
| `PUT /api/tasks/{id}/supplement` | 保存说明、示例与复核结果 |
| `POST /api/tasks/{id}/plan` | 根据选中项生成冻结计划 |
| `POST /api/plans/{id}/apply` | 提交明确 planHash 执行同步 |
| `POST /api/tasks/{id}/verify` | 只回读核对，不重新写入 |
| `POST /api/tasks/{id}/cancel` | 取消或请求在当前动作结束后停止 |
| `GET /api/tasks/{id}/reports/{format}` | 导出脱敏结果 |

检查和执行可返回任务 ID 后由页面轮询。重复提交同一 planHash 只返回原执行任务；不能启动第二次并行写入。新补充内容或选择变化需要重新生成计划。

注释计划采用同样的防重复执行约束，但状态与远端同步独立。扫描、候选生成、补丁导出不得调用应用接口；前端也不能把“生成草稿”做成默认勾选写源码和同步远端的复合按钮。

### 10.4 Apifox 集成方式

当前官方 CLI 文档列出了接口/模型读取、创建、更新和 CLI Schema 校验能力；仓库现有脚本也使用了这些命令。第一版优先复用这一条集成链路，具体字段和行为以实现时锁定并探测的 CLI 版本为准。[官方 CLI 文档](https://docs.apifox.com/doc-5637756)

建议调用顺序为：读取资源 → 获取对应 CLI Schema → 校验写入文件 → 执行写入 → 重新读取。CLI Schema 校验仅验证文件形状，不能证明业务语义或数据保留正确。

官方开放 API 还提供 OpenAPI 导入能力，可作为后续备选；首版选择逐资源写入，便于精确展示和核对操作范围。[OpenAPI 导入接口](https://s.apifox.cn/apidoc/docs-site/4478210/api-173409873)

本地 Swagger URL 应由本机工具读取。官方说明云端 URL 导入无法直接访问本机地址，因此不把 `localhost` URL 直接交给云端导入。[本地 URL 导入说明](https://docs.apifox.com/7607867m0)

### 10.5 实现前必须完成的能力探测

在专用测试项目和已有测试分支上准备少量样例，验证以下内容后才能开放写入功能。本设计阶段尚未执行这些操作。

| 待确认项 | 需要得到的证据 |
| --- | --- |
| 源码分析配置 | 实际项目引用、编译常量、partial/生成源码覆盖；无构建扫描的真实能力边界 |
| XML 消费链 | 所选项目生成 XML、实际产物位置、Swagger 加载，以及各标签的真实呈现 |
| 序列化映射 | JSON 命名、忽略、枚举表示、转换器和返回封装，不能只看 C# 属性名 |
| 注释补丁边界 | 能证明仅选中文档注释改变，已有未提交内容和业务 token 保持一致 |
| 生成链路 | 至少一种方式能由真实代码材料产出可审查候选，缺证据或模型失败能如实停留在未完成状态 |
| CLI 版本与运行依赖 | 版本、启动方式、可调用命令、稳定 JSON 输出方式 |
| 分支参数 | 列表、详情、创建、更新是否都访问指定分支，不意外回到主分支 |
| 更新合并语义 | 缺省字段、空值、嵌套参数/响应数组分别如何处理 |
| 字段和内部 ID | 能否保留参数、响应、示例等子项身份，以及原生设置 |
| 引用表示 | OpenAPI 引用如何映射到当前 CLI 模型 ID，组合和递归结构如何表示 |
| 失败形式 | 退出码、错误响应、超时和限流如何识别 |
| 写入后的读取 | 是否立即可见；如有延迟，以有限回读重试核对，不能重复写入 |
| 原子条件更新 | 是否存在可使用的版本条件；未确认前按存在竞态窗口设计 |

探测输出作为兼容性样例固定下来。CLI 升级后，未验证版本默认允许只读检查，写入须通过相关兼容验证。

### 10.6 可靠性、性能与本地访问

- 全链路使用 UTF-8，中文原样保存；新文本文件沿用 CRLF，不采用 GBK 解码兜底后静默继续。
- 子进程使用明确可执行入口和参数列表，不把项目名、路径等插入 shell 命令字符串；Windows 启动不弹出额外命令窗口。
- 解析退出码和结构化结果，不用“截取第一个左大括号到最后一个右大括号”作为唯一成功判断。输出无法可靠解析时停止。
- 同一任务中接口分页列表只读取一次；已读取详情按项目/分支/资源 ID 复用。执行前必要的重读不复用旧快照。
- 源码仅分析选中接口及必要依赖；按文件指纹复用语法树/符号材料，相关实现改变时使候选失效，不全库反复发送模型。
- 注释审阅、源码回写和远端同步分别计时；模型生成失败不影响已经保存的本地证据和人工编辑内容。
- 模型依赖采用引用图，不无限展开；模型只读取一次。写入首版串行，不引入并发写入。
- 全量影响扫描有明确进度和覆盖统计，取消后不把扫描不完整当成检查通过。
- 本地接口只监听回环地址，限制请求来源；写入接口要求本地会话校验，防止其他网页触发操作。
- Markdown/HTML 预览应转义和过滤危险内容；远端描述及示例不能在页面中执行脚本。
- 凭据由 CLI 管理，不读取其令牌文件，不写入计划、日志、分享报告或命令显示区域。
- 本工具拟定性能目标：在固定 1,000 接口/500 模型样例已载入后，本地差异计算 5 秒内完成。目标须实测；网络读取耗时另计并展示进度。

## 11. 开发阶段与交付物

建议先完成一个模块的小闭环，再扩大支持范围。阶段以可演示结果验收，不先按未经估算的人天承诺排期。

| 阶段 | 范围 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| M0 能力确认 | 固定 CLI、Roslyn/项目分析、XML 消费和序列化边界，验证受保护内容保留 | 兼容矩阵、源码与原生 JSON 样例、已知限制 | 确认注释可以准确定位和传播，最小远端更新不会丢内容 |
| M1 源码检查 | 仓库配置、符号定位、方法/入出参缺口、代码证据和中文页面 | 一个真实模块的注释缺口与依据报告 | 无 Swagger 时也能工作，未解析范围不假报完成 |
| M2 注释补全 | 一种实际生成链路、候选审阅、受限补丁、源码回写/导出及冲突保护 | 完整注释草稿和可审查补丁 | 从无注释样例生成有依据的说明，执行代码保持不变 |
| M3 契约检查与预览 | XML/Swagger 传播、响应补充、Apifox 差异、映射、影响与计划 | 可审阅的最终文档和同步清单 | 补源码之后的输入/输出在文档中正确呈现，阻断项不可绕过 |
| M4 同步闭环 | 目标重读、逐项写入、回读、日志和部分失败处理 | 测试目标的完整闭环 | 幂等、冲突、失败恢复等关键用例通过 |
| M5 首版试用 | 至少一个注释不完整的真实模块，再覆盖第二个模块 | 使用说明、验收记录、缺陷清单 | 达到第 12 节首版验收标准 |

如果 M0 发现精确远端更新无法可靠保留人工配置，先交付源码补全和只读检查的阶段版本；不能把不可靠的全量覆盖包装成“同步完成”。阶段版本不等于 v1.1 全部验收完成，也不能将注释补全再次推迟到无明确交付的后续版本。

第一版完成后再评估：Git 变更范围建议、命令行检查入口、测试用例草稿、更多 OpenAPI 版本。自动执行业务验收属于后续独立范围。

### 12.2 测试方式

- 结构比对、引用和风险规则使用固定输入/输出样例测试，覆盖请求与响应方向差异。
- 原生内容保留、更新语义、超时后核对及分支隔离，必须在专用 Apifox 测试目标中验证，不能只靠本地模拟宣称通过。
- 注释补全使用小型真实 C# 项目样例验证符号、XML 和补丁，比较前后执行语法 token、预处理指令与文件完整性；不得在测试里复制生产分析算法作为预期。
- 至少完成一个起初缺少方法/参数/DTO 注释的真实模块：“扫描源码 → 取证生成 → 审阅回写 → 定向生成文档 → 契约预览 → 同步 → 回读 → 再次检查无差异”。
- 对生成草稿进行人工语义验收：抽查每条规则是否由证据支持，是否遗漏条件、是否混淆 HTTP/业务状态。XML 合法和覆盖率达标不代表含义正确。
- 正式文档项目的第一次写入，使用已完成审核的小范围任务；不以全量项目作为首次验证样本。
