## 1. 产品定义

### 1.1 一句话定义

Apifox 助手是一个运行在开发者本机的工具：开发完成后，它从 C# 源码检查并补全接口注释，核对接口契约与 Apifox 文档的差异，经用户逐项确认后把有限的、可核验的变更同步到已有 Apifox 项目和分支，并输出可交接的报告。交互形态是桌面客户端（和/或经可行性评估后的宿主插件），不是网页。

### 1.2 目标用户

| 用户 | 核心诉求 | 使用方式 |
| --- | --- | --- |
| 后端开发（主要用户） | 日常开发后自动整理、更新 Apifox 文档，避免接口或字段变化后重复人工整理 | 执行完整旅程：扫描、补注释、检查、确认、同步 |
| 接口文档维护人员 | 检查缺说明、重复接口、坏引用，整理交接文档 | 以只读检查和报告为主，可不写入 |
| 前端开发 | 知道"这次到底改了什么" | 阅读同步报告与交接说明，不使用工具 |

第一版按单人本机使用设计，写入权限以当前 Apifox CLI 登录账号的实际权限为准，不另建用户、角色或审批系统。

### 1.3 解决的问题

1. **后端已改、文档未改**：接口新增、字段新增/移除、必填与类型变化后，Apifox 仍是最初的手工录入版本，靠人记忆逐个比对。
2. **说明缺失无人补**：方法、参数、请求/响应字段没有注释，Swagger 和 Apifox 里看不到参数含义、使用场景、响应字段含义。
3. **整理成本高且易错**：每次更新文档都要临时写脚本查找、更新、验证；批量导入又会覆盖人工说明。
4. **共享模型影响不清楚**：改一个共享模型，不知道会影响哪些接口。
5. **同步结果难判断**：命令返回成功，但字段、说明或引用是否真的写对无法确认。
6. **前端交接成本高**：前端需要重新询问本次变更内容。
7. **现有交互形态不好用**（用户裁定）：当前"窗口里嵌网页"的体验不符合桌面工具的使用预期，需要按真正的桌面/插件工作流重构。

### 1.4 交付形态与交互形态决定

**决定（2026-11-07，用户裁定）**：最终交互形态是**桌面客户端**和/或**宿主插件**（如 IDE 插件、Apifox 侧插件；具体宿主能力须先验证，不得虚构官方扩展 API）。撤销此前"维持 WinForms+WebView2 嵌网页形态不变"的产品决定。

- **桌面客户端是必选主交付，先行**（阶段 D，定义见 2.2）；**插件是并行评估方向**（阶段 P，定义见 2.3），评估产出 go/no-go 后再决定是否立项。
- **独立 Web 应用不是主界面，不是重点交付**。当前"桌面窗口内嵌网页"的体验定位为实现过渡，不再作为最终交互方案继续打磨。
- **本地业务能力复用，交互层重构**：源码分析、契约检查、同步计划与执行、报告等服务层与任务数据格式不动；页面层（HTML/CSS/JS 交互界面）按 2.4 的范围退场，由原生交互层替代。
- **headless 与本地服务保留为实现能力**，定位是自动化/CI 检查入口与桌面层的进程内服务底座，不是用户主产品；不把用户推回"打开浏览器使用网站"。
- 本阶段（本文档）只把重构定义清楚，不实施代码。

### 1.5 MVP 范围与非目标

**MVP 范围（按优先级）**

1. **交互形态重构（阶段 D）**：桌面客户端承载全部主工作流（定义与验收门槛见第 2 节；本阶段只定义）。
2. 项目配置：仓库、API 项目、允许回写范围、Swagger 来源、模块路径范围、Apifox 项目/分支/新接口目标目录与模板。
3. 源码注释闭环：扫描注释缺口 → 生成有证据的中文草稿 → 逐条审阅 → 受限回写源码或导出补丁 → 传播核对（XML/Swagger）。
4. 响应契约补全：追踪通用封装 data 的实际类型，形成逐接口、需确认的响应结构补充。
5. Apifox 检查：整分支只读概览 + 范围内接口/模型详情，结构差异、说明合并、质量检查、共享模型影响。
6. 同步：冻结计划 → 用户确认 → 逐项写入 + 回读核对，失败即停、部分完成如实记录。
7. 报告：Markdown/HTML/JSON 报告与前端交接说明。

**非目标（第一版明确不做）**

- 不把独立 Web 应用作为用户主界面或重点交付；不新增任何"浏览器里用网页"的用户路径。
- 不依赖或宣称任何未核实的插件宿主能力；Apifox 官方插件机制存在性未核实前，Apifox 侧集成只走已核实的 CLI 链路。
- 不自动删除任何远端资源（接口、模型、目录、用例、脚本）；不自动改名。
- 不自动发布未经确认的高风险变更；未通过写入兼容探测的 CLI 版本只允许只读检查。
- 不自动建项目/分支、合并分支、批量整理目录。
- 不自动修改业务执行代码、方法签名、校验属性；不做 DTO 重构。
- 不调用业务接口、不读写业务数据库；同步成功不等于业务接口经实际调用验证。
- 不接入消息平台自动发送报告；不建多人协作、云端部署。
- 不创建、修改或运行 Apifox 测试用例；不触碰 Mock 与环境变量配置。
- Git diff 自动映射影响范围、OpenAPI 3.1/Swagger 2/YAML 完整支持、多语言界面：列为后续评估，不进 MVP。

## 2. 交互形态重构（本阶段只定义，不实施）

### 2.1 重构目标与原则

1. **业务能力复用、交互层重构**：服务层（扫描/检查/计划/执行/报告）与任务数据格式原样复用；重构对象是承载它们的交互层。
2. **不做"壳里塞网页"的第二次**：新的桌面客户端必须是真正的桌面工作流——原生窗口与菜单、键盘快捷键、原生文件/目录选择、原生确认对话框、系统通知，多窗口协作（如差异详情、同步预览独立成窗）按需提供。
3. **不把用户推回浏览器**：主工作流从配置到报告全程在桌面客户端内完成。
4. **插件方向先验证后承诺**：任何"插件版"的说法在宿主能力核实前只是评估项。
5. **界面遵守第 6 节设计标准**：单一视觉来源、令牌化、状态完备、中文排版条款，重构第一屏之前先落设计基线文档。

### 2.2 阶段 D：桌面客户端（优先，P0）

**范围**：承载第 3 节全部旅程的阶段逻辑与确认点；任务列表、差异审阅、同步预览与执行、报告查看全部在原生窗口内完成。

**技术方向候选（按兄弟产品先例）**：

- WinUI 3（Windows App SDK）：AutoSnap（`src/AutoSnap.App`）与 PhotoLift（`src/PhotoLift.App` 规划）的先例；控件观感与 DPI 支持现代，但引入 Windows App SDK 依赖与 MSIX 打包面。
- WinForms 原生：WorkSwitch 的先例（其 `docs/方案.md` 第 6 节记录了不引入 WinUI 3 的三条理由：CI 可编译证据、单进程读同一份配置、为一屏只读列表引入新框架代价与收益不成比例）；无额外依赖、Linux CI 可编译，但现代控件与高 DPI 细节要自己做（WorkSwitch 用核心层度量表 + 逻辑像素换算解决）。

**D1 决策点**：技术栈在动手前按以下标准选定并写成决策记录（仿 WorkSwitch"先定边界再动代码"的纪律）：CI 可编译可断言、打包与分发成本、DPI 与无障碍、差异审阅所需控件能力（表格、树、结构化差异视图）、与本仓 .NET 8 代码的互操作。两条候选路线都有仓内先例，不预设结论。

**形态边界**：本工具是开发后使用的会话型工具，非常驻；默认单主窗口 + 按需辅助窗口，无托盘常驻需求（与 WorkSwitch 的托盘型形态区分）。

**验收门槛（全部满足才算 D 阶段交付）**：

| 门槛 | 内容 |
| --- | --- |
| G-D1 形态 | 主工作流（配置 → 任务 → 审阅 → 检查 → 计划 → 同步 → 报告）全部在原生窗口内完成，全程不要求打开浏览器；"在浏览器中打开"入口移除 |
| G-D2 设计基线 | 存在单一视觉来源设计文档；界面代码的颜色/字号/间距/圆角全部取自令牌，无就地发明值（抽检 + 机械检查） |
| G-D3 状态完备 | 每屏有状态表：空态、加载、执行中、错误、禁用、部分完成/中断，逐态定义控件可用性与文案（对照功能清单"设计验收"） |
| G-D4 中文排版 | 对照共享审查清单 A 节条款（全角标点、行首行尾禁则、正文行长、字号下限、字距非负、禁假斜体、字体栈顺序、中英文空隙）机械检查通过 |
| G-D5 真机观感 | 100% 与 200% DPI 截图各一套并按状态归档；观感由人复核（"接线正确"不等于"好看"） |
| G-D6 退场 | 原 Web 页面从用户路径移除（退场清单勾选，见 2.4） |

### 2.3 阶段 P：插件可行性评估（并行，产出 go/no-go，不承诺进版本）

**候选宿主与必须核实的能力**（在核实前，本文档不假设其存在或可用）：

| 候选 | 必须核实的项 | 现状 |
| --- | --- | --- |
| Apifox 官方插件/扩展机制 | 是否存在官方插件机制；能否读写接口/模型文档；能否调起本地进程或网络回调；分发与审核渠道 | 【待验证】。已核实的 Apifox 侧能力只有 CLI（只读检查可用，写入待探测）与开放 API 的导入能力（官方文档列出，未实测）；**不得虚构官方扩展 API** |
| VS Code 扩展 | 能否承载审阅 UI（WebView 面板或原生树/表）；能否调起本地 CLI 与服务；能否访问工作区与任务目录；分发渠道 | 公开扩展 API 存在，承载本工具审阅流程的具体可行性【待验证】 |
| Visual Studio / JetBrains 插件 | 同上（C# 开发者实际使用的 IDE 优先级调研） | 【待验证】 |

**评估前提下的职责假设（非承诺）**：插件做轻量入口（触发扫描、浏览注释缺口、查看报告），重审阅、冲突决策与写入确认留在桌面客户端；写入安全边界（第 8 节）不因宿主改变。

**出口**：一份评估报告，明确 go/no-go 与理由。no-go 不影响 D 阶段交付；Apifox 官方插件机制不存在时，该候选关闭，Apifox 侧集成保持 CLI 链路。

### 2.4 原 Web UI 的替代与退场范围

| 部分 | 处置 |
| --- | --- |
| 页面层（`Web/` 的 index.html/app.js/app.css 及其交互流程） | **退场**：作为用户界面在 G-D6 达成后移除；在此之前冻结（只修阻断性缺陷，不再新增交互打磨） |
| 本地 HTTP 服务与 `--headless` 模式 | **保留为实现能力**：自动化/CI 检查入口与桌面客户端的进程内服务底座；API 面不再为页面交互演化，不定位为用户主产品 |
| 服务层（源码分析、契约、同步、报告）与任务数据格式 | **复用不变** |
| 桌面壳（WinForms 窗口 + WebView2 宿主 + 会话令牌/Host/Origin 校验） | 宿主方式随 D1 决策点重新评估；本地访问控制与单实例、关闭确认等已验证的桌面行为作为需求带入选型，不作为不可动的实现保留 |

## 3. 核心用户旅程

以下旅程是**工作流级要求**（阶段、动作、确认点），不绑定具体控件实现；当前实现以 Web 页面承载（按 2.4 退场），重构后由桌面客户端承载同样的旅程。界面措辞以重构后的实现为准。

### 3.1 首次配置（一次性）

1. 启动桌面客户端，进入"项目设置"，填写仓库根目录与 API 项目（可浏览目录、"查找 API 项目"自动列出 `.csproj`，Web 项目优先）。
2. 检查 Apifox CLI：工具读取 CLI 版本与登录状态；未登录时按提示在终端执行 `apifox auth login`，工具复用登录态。
3. 选择有权限的 Apifox 项目和已有分支；配置新接口目标目录，可从既有接口提取受限模板（仅目录、状态、服务、鉴权、安全方案、公共头参数、标签，不克隆脚本/用例/Mock）。
4. 配置 Swagger 来源（文件或 JSON URL，可后补）与模块路径范围。
5. **写入兼容探测**：在专用测试项目的测试接口上运行往返验证（原样写回、临时改说明并恢复、整段写回参数/请求体/响应、导出与详情引用一致）。探测通过前，工具只允许只读检查。CLI 升级后需重新探测。

### 3.2 日常旅程：一次接口文档更新

任务按"源码注释 → 生成文档 → Apifox"三个阶段推进，界面始终给出唯一"下一步"。

1. **新建任务**：选择配置与模块，创建并直接开始源码扫描。
2. **源码注释**：查看注释缺口（方法用途、参数含义、请求/响应字段含义、枚举说明；不需要 Swagger）。用规则提取、模型生成或"导出材料 → 编码助手处理 → 导入结果"得到候选草稿，逐条对照代码证据审阅后接受；证据不足的业务含义（权限、单位、互斥、默认值）以问题形式留在任务中，不编造。
3. **注释应用**：预览源码差异后确认回写（只改 `///` 注释行，BOM、换行符、执行代码不变；文件被改动会拒绝写入），或仅导出补丁交由开发处理。
4. **生成文档**：可选执行定向构建（需确认），然后核对注释是否进入 XML 文档和 Swagger；旧生成物不算注释已生效。
5. **响应契约**：对 `data=object` 类接口，确认追踪到的实际返回类型与分支；有未解析点或多形状的契约不能确认。
6. **Apifox 差异**：配置了 Swagger 时首次检查先加载并冻结 Swagger，随后整分支只读概览 + 范围内详情读取，展示：新增接口、结构变化（含各层嵌套字段新增/移除）、说明合并结果、说明冲突、模型绑定与共享模型影响。逐项处理高风险变化与冲突后保存并重新检查。
7. **同步预览**：勾选接口（"全选可同步"只勾选无阻断、无待确认项的接口），生成冻结计划；预览显示每个动作的写入内容、受保护设置和排除原因。
8. **同步执行**：确认后逐项写入并立即回读核对；首个失败、结果不确定或核对失败即停止；可随时"重新核对（只读）"。
9. **报告**：导出 Markdown/HTML/JSON 报告与前端交接说明，自行发给前端/测试。

### 3.3 旅程变体

- **只检查不同步**：扫描、检查、导出报告，不写源码不写远端；源码应用与远端同步是两个独立确认。
- **无 Swagger**：源码扫描、注释补全与契约分析照常工作；Apifox 阶段结构保持远端现状，只合并说明，报告持续标注"源码已补全，生成文档未验证"。
- **离线比较**：导入两份 OpenAPI JSON 只比较结构，界面显示"离线检查"，同步禁用（无法证明 Apifox 原生设置与线上状态）。

## 4. 与 Apifox 的能力对接

### 4.1 集成方式

工具通过官方 Apifox CLI 以子进程方式访问 Apifox（`node` + cli.js + 参数列表，不经 shell），所有调用集中在 `Apifox/ApifoxCli.cs` 一个边界：显式传递项目 ID 与分支、解析退出码与结构化 JSON 输出、读取可有限重试、写入绝不自动重发、错误脱敏。凭据由 CLI 管理，工具不读取其令牌文件。

### 4.2 CLI 已核实支持的能力

以下事实来自开发笔记 2026-10-31 对本机 CLI 2.2.6 的实测，并已落入源码：

| 能力 | 已核实行为 |
| --- | --- |
| 版本与登录 | `--version`、`auth status`（工具据此判断只读/可写状态） |
| 项目/分支/目录 | `project list`、`branch list`、`folder list`；分支用 `--branch <名称>` 传递，不传为主分支 |
| 接口列表 | `endpoint list` 分页（`--page`/`--page-size`，meta 含 total/nextPage）、`--path-contains` 按路径过滤 |
| 接口/模型详情 | `endpoint get`、`schema get`、`schema list`（支持按名称过滤，无分页） |
| 整分支导出 | `export --format apifox --no-include-api-cases` 一次取得全部接口与模型引用（千级接口分支实测约 3 秒）；工具解析后立即删除导出文件，只保留引用概览 |
| 写入前校验 | `cli-schema get/validate`（endpoint-create/endpoint-update/schema-create/schema-update） |
| 输出协议 | 非 TTY 时 stdout 为单个 JSON 对象（success/data/error/meta）；退出码 0–5 各有明确含义 |
| 更新语义 | `endpoint update` / `schema update` 只提交传入的顶层字段；**数组和嵌套对象整体替换，不按 id 合并** |
| 模型格式 | nullable 写作 `"type": ["string","null"]`；字段顺序由 `x-apifox-orders` 表达 |

### 4.3 依赖 CLI、但需写入兼容探测后才能确认的能力

`endpoint create/update`、`schema create/update` 命令存在且工具已实现调用，但**从未对任何真实 Apifox 项目执行过端到端写入 + 回读验证**（开发笔记"尚未验证"一节）。在测试接口探测通过之前，以下问题按"未知"处理：

- 更新后参数/响应等子项的原有 id 与身份是否保留（整段替换语义下）。
- 脚本、Mock、用例、鉴权等受保护设置在整段替换 `parameters/requestBody/responses` 时是否安全。
- 创建后新资源 id 的返回方式与写入的立即可见性（是否存在延迟）。
- 错误、限流、超时的完整表现形式。

工具的策略：探测记录按 CLI 版本登记，未登记版本一律禁止生成同步计划（`Sync/CompatService.cs`、`Sync/SyncPlanService.cs` 的门禁）。

### 4.4 Apifox 各对象的利用方式

| Apifox 对象 | 工具的使用方式 |
| --- | --- |
| 项目 / 分支 | 配置中显式选择项目 ID 与分支名；同一项目/分支维度保存模型映射、执行锁与基线；探测验证分支隔离 |
| 目录 | 新接口创建前的目标目录，来自配置或从模板接口提取；无目标目录时新接口被阻断而不是随机放置 |
| 数据模型 | 显式映射"源组件名 → 远端模型 ID"，首次按同名生成唯一候选、经用户确认后保存；读取引用图计算共享模型影响；更新按依赖顺序先于接口 |
| 接口 | 身份 = HTTP 方法 + 精确路径；详情（`endpoint get`）作为比对与更新的权威内容；新建走受限模板 |
| 参数 / 请求体 / 响应 | 整接口作为一个结构同步单元（不按叶子字段拼装）；嵌套结构完整构造后整段写回，以适配"数组和嵌套对象整体替换"的已核实语义 |
| 接口说明 / 字段说明 | 目标 = Swagger + 已确认注释/响应契约 + 人工补充；合并规则见 5.5；已有说明默认保留，冲突需用户选择 |
| 请求/响应示例 | 已有示例作为受保护内容保留（保留效果待写入探测验证）；人工可在任务中补充示例（须为合法 JSON）进入目标；自动生成示例为待实现 |

### 4.5 CLI 升级与兼容策略

CLI 版本写入检查结果与计划；版本变化使已有计划过期。升级后未探测的新版本默认只允许只读检查；官方能力与本文的设计要求分开表述，官方文档列出 ≠ 本机已验证。

## 5. 变更检测与对比规则

### 5.1 变更检测的来源

| 来源 | 提供什么 | 说明 |
| --- | --- | --- |
| 源码扫描（Roslyn，无构建加载） | 接口清单、注释缺口、代码证据、响应 data 类型 | 只读，不执行 build/restore |
| 冻结的 Swagger（OpenAPI 3.0.x JSON） | 传输结构与框架描述 | 首次检查时加载并冻结；来源变化后计划过期 |
| Apifox 远端 | 整分支引用概览（export）+ 范围内接口/模型详情（逐资源 get） | 详情是比对与写入的权威内容 |

未提供 Swagger 时，结构没有可信来源，检查退化为"只合并说明"，不猜测结构。

### 5.2 对比基准

对比基准是"本次目标"与"Apifox 当前内容"：

- **本次目标** = 冻结 Swagger 的操作 + 已确认响应契约（替换 200 响应体）+ 说明条目（已确认注释优先于源码已有注释）+ 人工补充。
- **Apifox 当前内容** = 检查时逐资源读取的详情；生成同步计划时会重新读取，与检查时不一致则该接口被排除并要求重新检查；执行写入前第三次重读并核对指纹。
- 首次使用没有历史基线时，只能确认"源与远端不一致"，不断言哪一方更新；同步核对通过后保存基线，用于后续单侧/双侧变化的判断。

### 5.3 接口与字段身份匹配

| 对象 | 身份 | 匹配规则 |
| --- | --- | --- |
| 接口 | HTTP 方法（大写）+ 精确路径（保留大小写、尾斜线、参数名） | 不把标题或 operationId 当身份；远端同身份出现多个时阻断该身份 |
| 参数 | 位置（query/path/header/body）+ 名称 | 远端独有的 header/cookie 参数按受保护设置保留（Swagger 通常不声明鉴权头） |
| 字段 | JSON 属性路径（含嵌套与数组元素） | 序列化名称映射后比对；C# 名 ≠ JSON 名时以序列化配置为准，被忽略字段不进文档 |
| 模型 | 显式映射（源组件名 → 远端模型 ID） | 同名且唯一才生成候选；相近名、大小写不同、候选不唯一不自动绑定 |

### 5.4 重命名与删除的歧义处理

- **接口改名（路径或方法变化）**：按"新增接口 + 旧资源未匹配"展示。旧接口列在"远端有、源中没有"清单中，第一版不自动改名、不自动删除，由用户在 Apifox 处理。
- **字段改名**：没有证据区分"改名"与"新增 + 移除"，统一按新增 + 移除展示；移除字段的说明不拼接到别处，报告列出移除影响。
- **字段移除**：请求方向按"潜在不兼容"处理；响应方向同样要求确认。对已选资源内的字段删除属于结构更新，必须显示并确认，与"删除远端资源"严格区分。
- **共享模型**：修改共享模型前，沿引用图（含反向、已访问集合防递归）列出范围内与范围外的受影响接口；分支概览不完整时阻断模型更新，不把"没读取到"当作"没人引用"。

### 5.5 说明与场景：事实来源与置信度

每个出现在目标文档中的文字都有来源标注，置信度从高到低：

| 来源 | 置信度 | 合并规则 |
| --- | --- | --- |
| 人工补充（任务中编辑的说明/示例，含使用场景、参数规则、响应含义） | 最高（用户本人确认） | 直接进入目标；可对任意位置显式"保留现状" |
| 已确认的注释候选（审阅通过、且证据指纹未过期） | 高（用户审阅 + 代码证据） | 远端同位置已有不同说明时形成**冲突**，未选择前保留远端 |
| 源码已有有效注释 | 中（存在但未经本次审阅） | 远端为空则补充；不同则默认保留远端 |
| Swagger 描述 | 中（框架生成，可能过时） | 同上 |
| 规则提取的约束（校验特性、默认值、守卫条件、枚举显示名、响应 data 类型） | 高（代码可证实） | 只生成代码可证实的约束；方法/类型用途语义不做规则提取 |
| 模型生成候选 | 低（待审阅） | 必须引用本次扫描中存在的证据编号；无证据结论只能标"需业务确认"，不写成事实 |

原则：信息不足标记待补充而不是编造；"待确认"等草稿文字不发布到 Apifox；共享 DTO 属性只写可复用含义，仅特定接口成立的规则写入该接口说明；区分 HTTP 状态码与业务封装状态码（异步"已受理"不写成"已完成"）。

### 5.6 风险分级

| 等级 | 示例 | 行为 |
| --- | --- | --- |
| 普通 | 新增可选参数、补充说明 | 可勾选同步，仍需查看最终预览 |
| 潜在不兼容 | 新增必填请求参数、字段移除、类型变化 | 展示原因，逐项确认，不能被批量勾选带入 |
| 需人工判断 | 响应枚举新增、组合结构变化 | 不承诺兼容，要求人工处理或排除 |
| 阻断 | 悬空引用、远端重复身份、说明冲突未解决、目标已变化 | 禁用相关同步动作 |

风险判断区分请求与响应方向：请求允许值减少更严格，响应新增枚举值可能影响前端穷举处理，不套用同一条规则。

## 8. 写入安全与人工确认边界

以下边界为产品红线，任何后续实现（包括交互层重构与潜在的插件宿主）不得放松：

1. **两阶段独立确认**：源码注释回写与 Apifox 同步分别预览、分别确认；任一动作都不隐含另一个。
2. **预览先行**：同步主按钮是"确认同步 N 个接口、M 个模型"，绑定计划哈希；说明、选择、目标或 CLI 版本变化后原确认失效，必须重新预览。
3. **写入边界**：只写计划内资源；接口是结构同步的最小单元；更新前保存前态快照；更新只修改计划允许的部分并构造完整嵌套对象（适配整段替换语义）；无法可靠保留受保护设置的相关写入能力不开放。
4. **冲突检测**：计划生成时、执行前逐资源重读并核对指纹；目标被他人修改则该资源标为冲突、计划过期，不覆盖新修改。本地锁不承诺跨客户端原子性，界面提示同步期间避免修改相同资源。
5. **部分失败**：按依赖顺序串行执行（模型在前、接口在后），写入后立即回读（写入内容原样存在 + 未计划字段不变）；首个失败、结果不确定（超时不重发，先回读判断）或核对失败即停止后续写入；没有跨资源事务，部分完成如实记录，不谎报回滚。
6. **审计记录**：执行意图与逐项结果追加写入任务日志；保存远端前后快照、核对通过的基线；程序中断后启动时把未结束执行标为"已中断"，等待用户重新核对，不自动重放。
7. **创建防重**：创建前复查同身份资源；已有且一致记为无需修改；创建成功但未取得 ID 时按身份回读，只有唯一且一致才完成绑定，否则停止。
8. **不删除、不自动发布**：不自动删除远端资源；高风险变化与说明冲突未经逐项确认不得进入计划。
9. **本地安全**：本地服务只监听回环地址，校验 Host、Origin 与进程级会话令牌；凭据（模型服务密钥）由 DPAPI 加密保存在本机，不进入日志、报告与导出包；共享报告脱敏。
