## 1. 要决定的问题

阶段 D 的原生桌面客户端用什么技术栈实现。候选两条，均在本方案 §2.2 列出且有兄弟产品先例：

- **WinUI 3（Windows App SDK）**：AutoSnap 先例；
- **WinForms 原生**：WorkSwitch 先例（其 `docs/方案.md` §6 记录了拒绝 WinUI 3 的三条理由）。

决策按方案 §2.2 规定的六项标准逐项比较，不预设结论。

## 2. 决策

**选 WinForms 原生（net8.0-windows，与现有工程同一目标框架、同一工程文件），不引入 WinUI 3 / Windows App SDK。**

新的原生界面代码放在 `Desktop/Native/`，只依赖 WinForms 与 GDI+（本仓已有的两个框架引用），通过进程内服务容器（`Api/HelperHost`）直接复用扫描/检查/同步/报告服务层，不经 HTTP。现有 WebView2 壳按方案 §2.4 冻结为过渡实现，不在新原生界面中复用其页面层。

## 3. 逐项依据（六项标准）

| # | 标准 | WinUI 3 | WinForms 原生 | 结论 |
| --- | --- | --- | --- | --- |
| 1 | CI 可编译可断言 | Windows App SDK 的构建目标（XAML 编译、MSIX/打包链）绑定 Windows 工具链；本仓与协作环境的基础设施是 Linux 容器（本仓 CI 即 `dotnet build`/`dotnet test` 的环境）。WorkSwitch 拒 WinUI 3 的第一条理由即 CI 可编译证据 | `net8.0-windows` + `UseWindowsForms` 在 Linux 上可用 .NET SDK 编译（Windows 桌面引用包来自 NuGet，仅需编译不需运行）；WorkSwitch 有此先例记录。**注意**：本仓尚未在 Linux CI 上实际跑通过一次 `dotnet build`——见 §6 验证状态 | WinForms ✔ |
| 2 | 打包与分发成本 | 需要 Windows App SDK 运行时（MSIX 打包或解包部署 + 引导安装），分发表面积明显增大；AutoSnap 为此接受了 MSIX 面 | 沿用现有 `publish.ps1` 自包含单文件分发路径，无新增运行时依赖；当前用户拿到的是单个 exe | WinForms ✔ |
| 3 | DPI 与无障碍 | 控件观感与 DPI 支持现代，是它的主要优势 | PerMonitorV2 已在进程入口启用（`Desktop/DesktopApp.cs`），配合系统字体自动缩放；细节（逻辑像素、字号磅、不破版）需按 WorkSwitch `typeset` 档纪律自己做，且必须真机截图复核（G-D5） | WinUI 3 占优，但 WinForms 的差距有成熟方法弥补，不构成否决项 |
| 4 | 差异审阅控件能力（表格、树、结构化差异视图） | WinUI 3 内置控件集没有现成的数据表格控件（DataGrid 依赖社区工具包，其维护状态与大数据量表格的成熟度需另行验证）；树与等宽文本视图可用 | DataGridView（表格）、TreeView（模型/目录树）、等宽字体 TextBox/RichTextBox（差异文本）均为内置成熟控件，符合本工具"差异审阅工作台"的核心控件需求（方案 §6.3 已认定本产品信息密度高于单窗截图工具） | WinForms ✔ |
| 5 | 与本仓 .NET 8 代码的互操作 | 同样支持 .NET 8，但引入 CsWinRT 互操作层与 Windows App SDK 的初始化面；服务层复用没问题，互操作成本是纯增量 | 同一工程同一 TFM，服务层（`Api/ServiceRegistration.cs` 注册的全部单例）进程内直接注入，零互操作层 | WinForms ✔ |
| 6 | 形态匹配（会话型单主窗口 + 按需辅助窗口，无常驻） | 现代壳能力（磁贴、窗口亮显等）对本形态无用 | 足够；WorkSwitch 与本工具形态差异（托盘常驻 vs 会话型）不影响控件层选型 | 平手 |

## 4. 决策理由的归纳

1. **CI 可编译是硬门槛**：本产品的验收方式依赖"机械可判的检查落成自动断言"（设计验收 D1–D14、方案 §6.2 #14）。断言的前提是构建能在本仓现有的 Linux 工具链上跑起来。WinUI 3 在这条门槛上不可行；WinForms 可行（待首次实跑确认，见 §6）。
2. **差异审阅是主工作台**：表格与树是每天要看的东西，必须用成熟控件。WinForms 的 DataGridView/TreeView 内置且久经考验；WinUI 3 的表格故事弱。
3. **分发不能变重**：当前"单 exe 发给使用者"的分发方式是已验证的现状；WinUI 3 会引入 Windows App SDK 运行时与打包链，违背"有限迭代"。
4. **DPI/观感的短板用纪律补**：按方案 §6.2 #13（WorkSwitch `typeset` 档方法）与 G-D5 真机截图门槛补齐；这正是方案已写明的两条路线各自的代价。

## 5. 本决策要求后续实现遵守的边界

1. 界面代码只允许 WinForms/GDI+ 与 BCL；不引入 WebView2（新原生界面）、WPF、Windows App SDK 或第三方 UI 库。
2. 令牌唯一来源：`docs/DESIGN.md` 定义令牌值，`Desktop/Native/UiTokens.cs` 是其在代码中的唯一落点；界面代码不得就地发明颜色/字号/间距值（设计验收 D1）。
3. 字体栈有序回退（Segoe UI → Microsoft YaHei UI → Microsoft YaHei → SimHei → 系统回退），找到即停；字号档与间距档只取 `docs/DESIGN.md` 封闭档位。
4. DPI：进程入口 PerMonitorV2（现状保持），布局全部走逻辑坐标 + 系统字体缩放，不手工做像素换算；100%/200% 真机截图是 G-D5 门槛，未过不得宣称观感达标。
5. 服务层复用不变：写入确认、冲突检测、回读核对、部分失败如实记录等安全边界（方案 §8）在原生界面中语义不变；本切片不包含任何写入动作。
6. 已知代价（如实挂账，不冒充已解决）：WinForms 控件圆角需自绘，首版交付方角控件（与 D7 的差距记录在 `docs/DESIGN.md` 的"实现差距"节）；深色主题不做（§6.3 已裁定首版只浅色）。
