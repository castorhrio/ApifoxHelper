# Apifox 辅助工具：产品设计书 v1.0

版本：1.0  
日期：2026-10-30  
状态：开发设计稿，尚未实现  
适用对象：PNOS 后端开发、前端联调、接口文档维护人员  
暂定产品名：Apifox 助手

> 产品定位：把后端接口定义与 Apifox 文档之间的核对、补充和同步，整理成一个可预览、可选择、可核验的固定流程。
>
> 第一版交付：独立运行的本地网页工具。用户启动程序后，在浏览器中完成“选择项目 → 读取接口 → 查看差异 → 补充说明 → 确认同步 → 查看报告”。

## 1. 产品作用与立项理由

### 1.1 这个工具做什么

工具读取后端生成的 OpenAPI/Swagger JSON，以及指定 Apifox 项目和分支的接口文档，找出差异，协助用户补充业务说明，并把用户选定的修改同步到 Apifox。

它直接回答五个问题：

1. 后端已经提供、Apifox 还没有的接口有哪些？
2. 参数、请求体、响应体、枚举和必填规则有哪些不一致？
3. 哪些字段缺少说明，哪些业务规则需要人工补充？
4. 本次同步具体会改哪些接口和共享模型，会影响哪些已有接口？
5. 同步后，Apifox 中的内容是否与本次确认的目标一致？

### 1.2 当前项目中已观察到的基础

本节来自 2026-10-30 对当前仓库的只读检查，不代表线上运行验证。

| 现有基础 | 已观察到的行为 | 对产品设计的启示 |
| --- | --- | --- |
| `PNOS.API/Program.cs` | 配置 Swagger，并加载运行目录下的 XML 注释 | 优先消费实际生成的接口文档，不另写一套 C# 路由、DTO 解析器 |
| `docs/apifox/` | 已有多个模块的同步、修补和验证脚本 | 可以提炼共同步骤，减少每次新增一次性脚本 |
| WMS 文档同步脚本 | 按项目分页查找接口、校验更新文件、补充参数和业务说明 | 产品必须有项目配置、分页读取、写入前校验和业务说明维护 |
| 采购对账文档同步脚本 | 创建共享模型、维护引用、补充异步任务进度语义 | 同步要处理引用依赖；业务流程不能仅靠 Swagger 自动推断 |
| `.apifox/` 中的审计脚本 | 检查嵌套字段说明、模型引用、必填字段等 | 文档质量检查应进入固定流程 |

相关代码位置和复用建议见第 16 节。现有脚本作为实现参考，不直接当作稳定的公共库，也不在本次设计工作中修改它们。

### 1.3 解决的问题

| 问题 | 日常表现 | 工具提供的结果 |
| --- | --- | --- |
| 结构同步遗漏 | 后端新增字段，Apifox 参数或响应仍是旧结构 | 精确到字段位置的差异清单 |
| 文档维护重复 | 每次开发都临时写查找、更新、验证脚本 | 固定操作入口和统一配置 |
| 人工内容被覆盖 | 批量导入后，业务说明、示例或调试设置变化 | 明确内容归属，预览最终内容，保留受保护设置 |
| 共享模型影响不清楚 | 只想改一个接口，实际影响其他引用接口 | 展示共享模型的全部已识别接口影响范围 |
| 同步结果难判断 | 命令返回成功，但字段、引用或说明不正确 | 写入后回读核对和逐项报告 |
| 前端交接成本高 | 前端需要重新询问这次到底改了什么 | 可分享的变更说明 Markdown/HTML |

### 1.4 产品价值如何衡量

以下是上线后要测量的目标，不是已经取得的效果：

- 减少为普通接口文档更新编写一次性脚本的次数。
- 减少“后端已改、文档未改”的交接遗漏。
- 记录一次文档更新的人工操作耗时，与原有方式比较。
- 每次同步都能追溯输入版本、目标项目、实际修改和核对结果。
- 相同输入在同步完成后再次检查，结构差异为零，不产生重复接口或模型。

首轮用 5 次真实文档更新记录基准，再确定耗时改善指标，不先承诺节省百分比。

## 2. 使用者、场景与产品边界

### 2.1 使用者

| 使用者 | 核心任务 |
| --- | --- |
| 后端开发 | 改完接口后找出文档差异，补充规则，选择同步 |
| 文档维护人员 | 检查缺少说明、重复接口、错误引用，整理交接文档 |
| 前端开发 | 阅读变更报告，理解参数和返回值变化；无需拥有同步权限 |

第一版按单人本机使用设计。写入权限以当前 Apifox 账号的实际权限为准，不另建用户、角色或审批系统。

### 2.2 第一版支持的场景

- 新增接口后，在指定目录创建文档。
- 修改已有接口的参数、请求体、响应体和已支持的约束。
- 维护接口说明、字段说明、请求和响应示例。
- 按模块或接口范围检查文档质量。
- 预览并同步选定的接口及必要共享模型。
- 生成检查报告、同步报告和前端交接说明。

### 2.3 第一版边界

| 纳入第一版 | 后续再考虑 |
| --- | --- |
| 本地网页工作台、项目配置、任务记录 | 云端部署、多人实时协作 |
| OpenAPI 3.0.x JSON 文件或 JSON URL | Swagger 2、OpenAPI 3.1、YAML 的完整支持 |
| 比对、补充说明、选择同步、回读核对 | 自动解析业务代码、推断完整权限和状态机 |
| 已有项目、已有分支、已有目录 | 自动建项目、建分支、合并分支、批量整理目录 |
| 新建/更新接口及必要模型 | 自动删除接口、独立模型或自动移动目录 |
| 生成请求/响应示例草稿 | 创建、修改或运行 Apifox 测试用例 |
| 手工选择模块或路径范围 | Git diff 自动精确映射接口影响范围 |
| 本地快照和恢复参考信息 | 跨资源事务、自动回滚 |

工具的同步成功表示文档写入和核对成功，不表示业务接口经过实际调用验证。第一版不调用 PNOS 登录、导入、计费等业务接口，不读写业务数据库。

## 3. 产品形态与使用流程

### 3.1 交付形态

- 独立 Windows 本地工具，启动后打开默认浏览器。
- 使用中文界面；用户通过表单、差异列表和预览完成操作。
- 本地进程读取文件、访问 Swagger 地址，并通过 Apifox CLI 访问 Apifox。
- 配置和任务资料保存在本机，无需额外部署数据库或云服务。
- 第一版复用已安装 CLI 的登录态；不在网页中收集 Apifox 令牌。

启动程序名暂定 `ApifoxHelper.exe`，是拟定的交付方式，目前没有该程序。

### 3.2 首次配置

1. 启动工具，进入“项目设置”。
2. 检查 Apifox CLI 是否可用、版本是否符合已验证的兼容要求。
3. 如果尚未登录，按页面说明在本机终端完成 CLI 登录，再点击“重新检查”。
4. 选择有权限访问的 Apifox 项目和已有分支。界面持续显示项目名称、ID 和分支。
5. 添加后端文档来源：本地 JSON 文件，或开发/测试服务的 Swagger JSON 地址。
6. 配置常用模块的路径范围、新接口目标目录，以及新接口所需的服务和鉴权模板。
7. 点击“保存并读取”，验证能读取所选范围。读取成功只代表读权限已验证，不承诺写权限。

配置里要区分 Apifox 项目 ID、Apifox 分支和 PNOS 业务项目上下文。它们是不同概念，不能共用一个“项目 ID”字段。

### 3.3 日常使用：更新一个模块

1. 开发完成后，确保提供的 Swagger 来源与本次代码版本对应；工具不自动编译或启动 PNOS。
2. 选择项目配置，点击“新建检查任务”，填写任务名称和来源版本备注。
3. 选择模块、路径前缀或具体接口，点击“开始检查”。
4. 查看差异摘要，打开变化接口，确认字段变化和共享模型影响。
5. 对需要维护的说明或示例进行编辑，处理冲突和待确认项。
6. 勾选要同步的接口；系统自动加入必要模型依赖，并展示额外影响范围。
7. 查看最终内容和写入清单，点击“确认同步”。
8. 工具校验目标是否变化，执行同步，并回读核对。
9. 下载报告；将交接说明发给前端或测试人员。

第 9 步由用户自行发送，工具第一版不连接消息平台。

### 3.4 只检查，不同步

用户可以在第 4 步直接导出检查报告。检查行为不修改 Apifox。

没有在线访问条件时，可以导入两份 OpenAPI JSON 离线比较；此模式只能检查结构，无法证明 Apifox 原生设置、重复接口及当前线上状态完整，页面必须显示“离线检查”，同步按钮禁用。

### 3.5 一个具体例子

以下是假设场景，用于解释产品行为，不表示这些变更尚未在当前系统完成：

后端为 `GET /api/finance/BillList` 增加 `ArchiveId` 参数。检查后页面展示：

| 检查项 | 展示结果 |
| --- | --- |
| 参数变化 | Query 新增 `ArchiveId`，整数，是否必填以输入契约为准 |
| 文档质量 | 新参数缺少业务说明，提示补充 |
| 业务规则 | 用户填写“与 ClientId 互斥；使用场景和取值来源……” |
| 既有配置 | 保留已有接口 ID、目录、服务、鉴权和脚本 |
| 最终预览 | 显示新增参数及合并后的说明，列出本次会修改的内容 |
| 同步结果 | 回读参数、说明及受保护设置；一致才标记为核对通过 |

“与 ClientId 互斥”必须来自人工确认的规则或已有文档，不能从两个字段同时存在推断出来。

## 4. 页面设计

第一版采用一个工作台，包含“项目设置、检查任务、任务详情、历史报告”四个主要入口。任务详情内部完成差异查看、说明编辑和同步预览，避免拆成过多页面。

### 4.1 项目设置

| 字段/区域 | 说明 |
| --- | --- |
| 配置名称 | 例如“PNOS 开发文档” |
| CLI 状态 | 可执行入口、版本、登录状态、兼容性检查结果 |
| Apifox 项目/分支 | 从可访问资源中选择；保存明确 ID 和分支标识 |
| Swagger 来源 | 文件或 JSON URL；不接受 Swagger UI 页面地址 |
| 来源版本备注 | 用户填写提交号、构建号或版本描述，可为空但显示“未绑定代码版本” |
| 模块范围 | 模块名与路径前缀映射，例如“财务”→`/api/finance/` |
| 新接口目标 | 已有目录、服务、明确选择的鉴权/公共参数模板 |
| 操作 | 检查连接、保存、导出不含凭据的配置 |

新接口模板只复制明确列出的配置字段，不克隆任意接口的脚本、用例、Mock 或历史请求。

### 4.2 检查任务列表

每项显示任务名称、项目/分支、来源备注、创建时间、状态、变化接口数和未处理项数。

操作：新建检查、查看结果、导出报告、基于相同配置重新检查。重新检查创建新任务，不覆盖旧报告。

### 4.3 任务详情：差异工作台

```text
Apifox 助手    PNOS / 指定分支    来源：本地 Swagger    版本备注：...

任务：财务接口文档更新
新增 2   结构变化 3   说明变化 1   冲突 1   无变化 20

[模块] [变化类型] [风险] [关键词]             [导出检查报告]

接口列表                      差异详情
☐ GET  /api/finance/...        变化摘要 | 字段对比 | 业务说明 | 最终预览
☐ POST /api/finance/...        位置：query.ArchiveId
                              Apifox：不存在
                              目标：integer / optional
                              来源：Swagger
                              说明：[填写业务用途...]

共享模型影响：模型 X → 选中接口 2 个，范围外接口 3 个
待处理：1 个冲突，2 项业务说明需要确认

已选择 2 个接口，将涉及 1 个模型              [生成同步预览]
```

关键交互：

- 初次进入时同步项默认不勾选。
- 差异详情显示旧值、新值、字段位置、来源和风险原因，不能只有两个大段 JSON。
- 删除字段、类型变化等高风险项必须逐项确认，不能被“选择普通变化”批量带入。
- 用户可以编辑说明和示例；结构来自输入契约，不能在此随意改成与 Swagger 不同的类型。
- 生成目标示例时使用虚构值或变量占位；示例须通过当前支持范围内的结构校验后才能提交。
- 未填写的业务说明留在本地待办，不把“待确认”等草稿文字发布到 Apifox。
- 同一接口默认作为一个结构同步单元；不开放任意叶子字段拼装，避免产生不完整契约。

### 4.4 同步预览

必须展示：目标项目和分支、接口创建/更新清单、模型清单、共享模型影响、说明改动、保留设置、校验结果及未支持内容。

主按钮为“确认同步 N 个接口、M 个模型”。确认绑定当前计划版本；说明、选择或目标变化后，原确认失效，需要重新预览。

如果只有文档说明缺失，可由用户明确选择“保留现状，本次不补充”；报告保留未完成事项。未解析引用、重复身份、未识别的写入结构等阻断项不能跳过。

### 4.5 结果与历史报告

逐项显示“已写入并核对、写入结果待确认、核对失败、冲突、未执行、无需修改”。

报告包括实际写入的接口链接、未完成原因、来源版本和未验证范围。接口链接须使用平台返回或验证过的链接格式，不能自行猜测链接后宣称可用。

提供“重新核对”和“生成后续任务”；第一版没有无条件重放写入或一键回滚按钮。

## 5. 功能需求与完成标准

| 编号 | 功能 | 第一版要求 | 完成标准 |
| --- | --- | --- | --- |
| F01 | 项目配置 | 保存项目、已有分支、来源、范围和新接口模板 | 切换配置后，所有读写使用同一明确目标 |
| F02 | 文档读取 | 读取 OpenAPI 3.0.x JSON，保存输入快照 | 非法或不支持输入显示原因，不继续同步 |
| F03 | Apifox 快照 | 分页列出接口/模型，读取所需原生详情 | 分页和必要依赖完整；读取失败不能按资源不存在处理 |
| F04 | 结构比对 | 比较请求、响应和模型结构，展示字段位置 | 固定样例集能复现预期差异，不受无关元数据干扰 |
| F05 | 质量检查 | 缺少说明、重复接口、悬空引用、通用响应缺少具体 data 类型等 | 每项有证据位置，区分建议与阻断 |
| F06 | 业务补充 | 维护说明、枚举含义和示例 | 编辑可保存、可预览、可追溯到具体接口/字段 |
| F07 | 影响分析 | 计算共享模型依赖及范围外接口引用 | 未完整读取影响范围时，相关模型更新被阻断 |
| F08 | 同步计划 | 冻结选中项、依赖、目标内容和前置指纹 | 预览内容与实际执行计划一致 |
| F09 | 选择同步 | 新建/更新接口及必要模型，保留受保护内容 | 只写计划内资源，重复执行不会盲目重复创建 |
| F10 | 回读核对 | 比较目标结构、说明和受保护字段 | 写入命令成功但结果不一致时，不能标记成功 |
| F11 | 报告 | 本地保存完整任务，导出脱敏 Markdown/HTML/JSON | 共享报告不含令牌、Cookie、真实请求敏感值 |

“通用响应缺少具体 data 类型”等规则为项目可配置检查；若源 Swagger 自身只有通用对象，只提示源契约不充分，不编造具体响应类型。

## 6. 比对规则与判断依据

### 6.1 数据来源和优先级

| 内容 | 默认依据 | 冲突处理 |
| --- | --- | --- |
| 方法、路径、参数位置、类型、必填、约束、请求/响应结构 | 用户选定的源 Swagger | 与已确认补充规则矛盾时阻断，不静默选一边 |
| 已有接口标题、目录、标签、服务、鉴权、公共参数 | Apifox 当前内容 | 第一版保留；Swagger 相关变化仅列待确认 |
| 已有业务说明、字段说明、请求/响应示例 | Apifox 当前内容 | 同一语义位置保留；结构变化影响说明时提示复核 |
| 用户明确编辑的说明/示例 | 当前任务中确认的补充内容 | 覆盖范围须精确到对应位置，并进入预览 |
| 新接口所需目录、服务和鉴权 | 项目中明确选择的模板 | 无模板或无法确认时阻断创建，不随意复制其他接口 |
| 脚本、Mock、用例、环境变量、鉴权密钥 | Apifox 原生配置 | 不作为同步目标；更新时保留并核验可读取的相关设置 |

Swagger 未声明鉴权，不代表业务允许匿名；不能据此清空已有鉴权。业务权限、互斥参数、进度状态和幂等规则，必须有人工确认内容。

### 6.2 接口与模型身份

- 接口身份为“Apifox 项目 + 分支 + HTTP 方法 + 精确路径”。方法统一大写，路径保留大小写、尾斜线和参数名。
- 不把接口标题或 `operationId` 当作唯一身份；不自动合并 `/a/{id}` 与 `/a/{key}`。
- 路径或方法变化按“新增 + 旧资源未匹配”展示。第一版不自动改名或删除旧接口。
- Apifox 同一身份出现多个接口时，阻断该身份同步并列出候选，不能取第一条覆盖。
- 模型采用显式映射；首次可按完全同名生成候选，唯一且经用户确认后保存“源模型键 → 远端模型 ID”。
- 模型名称相近、大小写不同或候选不唯一时不自动绑定。
- 远端 ID 是平台身份，不能用随机生成 ID 替换已有资源 ID。

### 6.3 第一版比较范围

| 范围 | 比较内容 |
| --- | --- |
| 参数 | path/query/header/cookie、名称、必填、类型、格式、枚举、默认值、已支持约束 |
| 请求体 | required、媒体类型、JSON 结构；multipart 文件字段和支持的普通字段 |
| 响应 | HTTP 状态码、媒体类型、响应头、结构、nullable、数组和嵌套属性 |
| 模型 | properties、required、items、additionalProperties、支持的校验约束和引用 |
| 文档 | 标题、说明、字段说明、示例的有无及用户明确编辑的差异 |
| 保留项 | 目录、服务、鉴权、公共参数、可读取的脚本关联和既有示例等 |

必须区分 HTTP 响应码与 `PNOSActionResult.statusCode` 业务状态。工具不以 HTTP 200 自动判断业务成功，也不把异步任务“已受理”描述成“已完成”。

### 6.4 风险分级

| 等级 | 示例 | 页面行为 |
| --- | --- | --- |
| 普通 | 新增可选请求参数、补充说明 | 可选择同步，仍需查看最终预览 |
| 潜在不兼容 | 新增必填请求参数、删除响应字段、改变类型、收紧范围 | 展示原因，逐项确认 |
| 需人工判断 | 响应枚举新增、组合结构变化、未识别格式或业务语义变化 | 不承诺兼容，要求人工处理或排除 |
| 阻断 | 悬空引用、重复身份、冲突未解决、目标发生变化 | 禁用相关同步动作 |

风险判断区分请求和响应方向。例如请求允许值减少通常更严格，响应新增枚举值可能影响前端穷举处理；不能套用同一个“枚举增加=兼容”规则。

### 6.5 标准化与引用

- 消除纯对象键顺序、可作为集合处理的 `required` 等造成的假差异；不随意重排全部数组。
- `enum` 按值及类型比较；数字 `1` 与字符串 `"1"` 不能视为相同。
- 显式区分“不存在”“null”“空数组”“空对象”，不统一丢弃。
- 本地 `components/schemas` 与 Apifox 原生模型 ID 先映射为逻辑引用再比较，不能直接比较引用字符串。
- 通过引用图遍历，使用已访问集合处理递归模型，不把所有模型无限展开。
- `allOf/oneOf/anyOf` 保留其组合语义；第一版不做复杂等价推理，无法可靠转换的写入标为不支持。
- 第一版只自动处理文档内引用；外部 URL/文件引用提示不支持并阻断相关同步。
- 未知扩展原样保留在已有远端资源中；若源结构包含可能改变验证/序列化语义且尚未支持的部分，不能忽略后同步。

## 7. 业务说明与人工内容保护

### 7.1 业务说明编辑模板

每个接口可维护以下内容；不是所有接口都必须填满模板。

| 区域 | 内容举例 |
| --- | --- |
| 使用场景 | 哪个页面、哪个操作调用 |
| 前置条件 | 所需档案、配置或业务状态 |
| 项目与权限 | 项目上下文的来源、允许操作的范围 |
| 参数规则 | 参数取值来源、互斥、依赖、默认业务含义 |
| 操作结果 | 成功、失败、部分完成或已受理的含义 |
| 异步后续 | taskId 来源、轮询接口、完成/失败条件 |
| 示例 | 虚构请求、响应和必要说明 |

模板只生成待填写结构，不生成未经确认的业务结论。第一版不依赖 AI 服务。

### 7.2 合并规则

1. 已有接口说明默认保留；用户可以明确编辑完整说明，提交前查看全文差异。
2. 字段说明按接口、请求/响应位置和属性路径定位；仅保留仍存在且能准确对应的字段说明。
3. 字段被移除时，其说明不拼接到别处；报告列出移除影响。
4. 字段类型或约束变化时，已有说明和示例标为需要复核；原有示例若不符合新结构，不自动发布为有效示例。
5. 未进行人工编辑时，不能用空值或 Swagger 缺省值覆盖已有人工说明。
6. 已有示例在更新后仍需保留；用户明确替换的示例才作为本次目标。新增示例与原生用例是不同资源。

### 7.3 首次使用与后续使用

首次没有历史基线时，只能确认“源和 Apifox 当前不一致”，不能断言哪一方是最近修改。所有写入项均需用户选择和确认。

同步核对通过后，为成功资源保存源结构、已确认补充内容和远端结果的基线。后续检查若源与远端都改变同一受管理部分，标记冲突；只有单侧改变时可以提出合并建议，但仍由当前计划确认。

说明编辑以本次读取的远端内容为基础，不把旧基线中的人工文字强行覆盖回去。基线不能替代应用前的目标重读。

## 8. 同步规则、失败处理与恢复

### 8.1 同步前的必要条件

- 项目、分支、源快照和模型映射明确。
- 所选接口及必要依赖全部可解析。
- 首次绑定、潜在不兼容变化、业务内容复核已完成。
- 同步计划及写入文件通过本工具校验和当前 CLI Schema 校验。
- 写入前快照与执行意图日志已成功保存；本地存储失败不能继续写入。
- 在开始执行和每个资源写入前重读相关目标，检查指纹与计划一致。
- 应用前重新计算源文件指纹；URL 来源重新读取并核对。来源变化后计划过期，需重新检查。

当前任务使用冻结的输入快照，不在执行中静默混入新的源内容。

### 8.2 共享模型影响控制

修改已有共享模型前，读取当前分支全部接口和模型的必要引用信息，计算直接和间接引用。不能只查当前选中模块。

- 页面同时列出范围内、范围外受影响接口。
- 范围外影响必须在预览中明确确认；无法确认时可排除该模型及依赖更新。
- 全部必要分页/详情读取未完成时，阻断该模型变更；不把“没读取到”当作“没人引用”。
- 未选择的接口不单独改写，但引用共享模型后文档表现可能变化，报告必须如实说明。
- 第一版不完整分析用例脚本等任意文本里的模型依赖，这部分列为人工复核范围。

新增模型按依赖顺序创建，再更新引用它们的接口。新建互相递归引用模型若需要预建空壳等额外步骤，第一版阻断并要求人工准备；已有递归模型在映射完整且可表示时可以比对和更新。

### 8.3 执行方式

首版按资源顺序执行，避免同时写同一目标。

1. 校验计划和源版本。
2. 获取同一项目/分支的本地执行锁。
3. 再次确认目标当前内容未变，并保存前态快照。
4. 按依赖顺序处理模型，再处理接口。
5. 每个资源写入后立即回读，核对受管理内容及应保留设置。
6. 保存逐项结果。首次写入错误、结果不确定或核对失败后停止后续写入。
7. 仅对已核对通过的资源推进基线，最后生成报告。

确认粒度是同步计划，不需要每个正常资源再次弹窗；计划变化才要求重新确认。

### 8.4 状态定义

| 状态 | 含义 |
| --- | --- |
| 检查中 | 正在读取和计算，没有远端修改 |
| 待处理 | 有冲突、阻断或需要确认的内容 |
| 可预览 | 已能生成可审阅计划 |
| 待确认 | 计划已冻结，等待用户确认 |
| 执行中 | 已开始写入，部分资源可能已生效 |
| 已核对通过 | 所有计划内动作均回读一致 |
| 部分完成 | 至少一个资源核对通过，其他动作未完成 |
| 失败 | 无已核对通过动作，且存在失败或未知结果；不代表远端一定未改变 |
| 已过期 | 源、目标或计划版本变化，需要重新检查 |
| 已取消 | 用户在写入前取消，或执行中请求在当前动作结束后停止；保留已发生结果 |

资源级状态至少包括：待执行、已写入待核对、已核对通过、写入失败、结果待确认、核对失败、冲突、未执行、无需修改。

### 8.5 超时、重试与重复创建

- 读取操作可有限重试；建议最多 3 次，并遵守平台限流信息。
- 写入超时不能直接重发，先标记“结果待确认”，按 ID 或接口身份回读当前状态。
- 创建动作前复查同身份资源；已有且目标一致时记为无需修改，已有但不一致时重新生成更新计划。
- 创建后未取得 ID 时，重新查询候选；只有唯一且可核对一致时才能完成绑定，否则停止。
- 程序崩溃重启后先核对日志中未结束的动作，不能直接重放。
- 重新处理失败项时生成后续计划，成功项先检查是否已达目标，不反复创建。

本地锁不能阻止其他用户同时操作 Apifox。若平台能力探测未确认原子条件更新，执行前指纹检查仍有竞态窗口；界面提醒同步期间避免修改相同资源，产品不承诺跨客户端原子性。

### 8.6 保护与恢复边界

- 首版不自动删除接口、独立模型、目录、用例或脚本。
- 对已选资源内的字段删除属于结构更新，必须显示并确认；不与“删除远端资源”混为一谈。
- 更新使用当前远端资源作为基础，仅修改计划允许的部分。若 CLI 对嵌套对象采用替换语义，需要构造完整嵌套对象以保留其他项。
- 如果 CLI 更新会重置受保护设置且无法可靠保留，相关写入能力不能开放。
- 没有跨资源事务；模型写入成功而接口失败时，模型可能已生效，应显示部分完成。
- 第一版保存可用于排查和人工恢复的前后快照，提供平台历史记录恢复指引，不承诺快照可无损一键导回。
- 恢复操作须重新核对当前状态，不能覆盖同步后其他人的修改。

## 9. 本地数据与输出设计

### 9.1 存储方式

首版使用 JSON 文件和任务目录，无需数据库。建议用户数据目录为 `%LOCALAPPDATA%\PNOS\ApifoxHelper\`，不写入 PNOS 业务表。

```text
ApifoxHelper/
  profiles/                 项目配置，不含令牌
  mappings/                 模型和接口的确认映射
  baselines/                各项目/分支/资源的成功基线
  tasks/<taskId>/
    task.json               任务、目标、来源版本及状态
    source.openapi.json     冻结的源文件
    remote-before/          写入前原生详情快照，受本机访问权限保护
    supplement.json         本次人工确认的说明和示例
    diff.json               差异及判断依据
    plan.json               冻结的同步计划
    journal.jsonl           执行意图和逐项结果
    remote-after/           回读结果
    report.json             机器可读结果
    report.md               可分享检查/同步报告
    handoff.md              前端交接说明
```

普通配置、映射和补充说明可由用户显式导出到代码仓库；令牌、原生快照和原始执行输出不进入共享导出。快照可能含受保护配置，需限制本机访问；展示和分享时使用脱敏副本。

### 9.2 关键数据对象

| 对象 | 必要字段 |
| --- | --- |
| ProjectProfile | id、name、apifoxProjectId、branch、sourceType、sourceLocation、scope、newEndpointTemplate、CLI 兼容信息 |
| CheckTask | id、profileSnapshot、sourceHash、sourceVersionNote、createdAt、status、coverage、toolVersion、cliVersion |
| ResourceMapping | targetProject、branch、sourceKey、remoteId、confirmedAt |
| DiffItem | id、resourceKey、location、before、after、source、risk、reason、blocking、resolution |
| Supplement | resourceKey、fieldLocation、description/examples、reviewedContractHash |
| SyncPlan | id、taskId、version、hash、target、actions、dependencies、preconditions、confirmedAt |
| PlanAction | actionId、resourceKey、kind、remoteId、beforeHash、desiredHash、payloadPath、dependsOn |
| ActionResult | actionId、state、remoteId、startedAt、finishedAt、verification、redactedError |
| Baseline | resourceKey、verifiedSource、verifiedSupplement、verifiedRemoteHash、verifiedTaskId |

指纹只忽略明确无业务意义的元数据，不忽略鉴权、脚本、服务等受保护设置。计划执行期间原子保存状态文件，执行日志追加写入。

### 9.3 报告结构

```text
任务：财务接口文档更新
目标：项目名称 / 项目 ID / 分支
来源：文件或地址 / 指纹 / 用户填写的版本备注

执行结果：已核对通过 3，核对失败 1，未执行 2
文档质量：未补充说明 2，人工确认后保留现状 1

1. 实际新增/更新了哪些接口和模型
2. 参数及响应变化，潜在不兼容项
3. 共享模型对范围外接口的影响
4. 人工补充的业务说明
5. 未完成动作、原因和后续处理方式
6. 检查覆盖范围与未支持内容
7. 验证边界：只核对文档，未执行业务接口
```

报告必须分别统计“文档一致性”“文档完整性”“业务运行验证”。结构一致但说明仍缺失时，不能展示为所有工作已完成。

## 10. 技术落地方案

### 10.1 推荐实现

建议使用独立 .NET 8 应用，提供本地 HTTP 接口并承载静态网页。界面可先采用普通 HTML/CSS/JavaScript，保持单进程运行，不要求另建前端服务。

```text
浏览器中的中文工作台
           |
本地 .NET 8 应用（仅监听回环地址）
   |              |                 |
OpenAPI读取    比对/计划/报告       Apifox CLI 调用
   |              |                 |
文件或JSON URL  本机JSON任务目录     Apifox项目及分支
```

选择这一方案是为了沿用现有 .NET 开发经验，同时让工具独立于 PNOS API、数据库及发布流程。具体 UI 框架可以在实现时按团队已有基础决定，不影响本文的行为要求。

### 10.2 最小职责划分

建议保持少量清晰职责：来源读取、Apifox 调用、结构比对、同步执行、报告输出。先用普通类和函数实现，不预设插件系统、策略层或通用工作流引擎。

Apifox 调用集中在一个边界，负责明确传递项目和分支、分页、超时、结果解析、错误脱敏以及当前 CLI 版本兼容。避免在不同页面各自拼命令。

### 10.3 本地接口草案

以下是本工具拟定接口，不是 PNOS 或 Apifox 已有接口。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/capabilities` | 当前 CLI、登录和功能兼容情况 |
| `GET/POST /api/profiles` | 查询/创建项目配置 |
| `PUT /api/profiles/{id}` | 修改配置 |
| `POST /api/tasks` | 根据配置快照创建检查任务 |
| `GET /api/tasks/{id}` | 查询任务摘要、进度和状态 |
| `GET /api/tasks/{id}/diffs` | 按风险和资源筛选差异 |
| `PUT /api/tasks/{id}/supplement` | 保存说明、示例与复核结果 |
| `POST /api/tasks/{id}/plan` | 根据选中项生成冻结计划 |
| `POST /api/plans/{id}/apply` | 提交明确 planHash 执行同步 |
| `POST /api/tasks/{id}/verify` | 只回读核对，不重新写入 |
| `POST /api/tasks/{id}/cancel` | 取消或请求在当前动作结束后停止 |
| `GET /api/tasks/{id}/reports/{format}` | 导出脱敏结果 |

检查和执行可返回任务 ID 后由页面轮询。重复提交同一 planHash 只返回原执行任务；不能启动第二次并行写入。新补充内容或选择变化需要重新生成计划。

### 10.4 Apifox 集成方式

当前官方 CLI 文档列出了接口/模型读取、创建、更新和 CLI Schema 校验能力；仓库现有脚本也使用了这些命令。第一版优先复用这一条集成链路，具体字段和行为以实现时锁定并探测的 CLI 版本为准。[官方 CLI 文档](https://docs.apifox.com/doc-5637756)

建议调用顺序为：读取资源 → 获取对应 CLI Schema → 校验写入文件 → 执行写入 → 重新读取。CLI Schema 校验仅验证文件形状，不能证明业务语义或数据保留正确。

官方开放 API 还提供 OpenAPI 导入能力，可作为后续备选；首版选择逐资源写入，便于精确展示和核对操作范围。[OpenAPI 导入接口](https://s.apifox.cn/apidoc/docs-site/4478210/api-173409873)

本地 Swagger URL 应由本机工具读取。官方说明云端 URL 导入无法直接访问本机地址，因此不把 `localhost` URL 直接交给云端导入。[本地 URL 导入说明](https://docs.apifox.com/7607867m0)

### 10.5 实现前必须完成的能力探测

在专用测试项目和已有测试分支上准备少量样例，验证以下内容后才能开放写入功能。本设计阶段尚未执行这些操作。

| 待确认项 | 需要得到的证据 |
| --- | --- |
| CLI 版本与运行依赖 | 版本、启动方式、可调用命令、稳定 JSON 输出方式 |
| 分支参数 | 列表、详情、创建、更新是否都访问指定分支，不意外回到主分支 |
| 更新合并语义 | 缺省字段、空值、嵌套参数/响应数组分别如何处理 |
| 字段和内部 ID | 能否保留参数、响应、示例等子项身份，以及原生设置 |
| 引用表示 | OpenAPI 引用如何映射到当前 CLI 模型 ID，组合和递归结构如何表示 |
| 失败形式 | 退出码、错误响应、超时和限流如何识别 |
| 写入后的读取 | 是否立即可见；如有延迟，以有限回读重试核对，不能重复写入 |
| 原子条件更新 | 是否存在可使用的版本条件；未确认前按存在竞态窗口设计 |

探测输出作为兼容性样例固定下来。CLI 升级后，未验证版本默认允许只读检查，写入须通过相关兼容验证。

### 10.6 可靠性、性能与本地访问

- 全链路使用 UTF-8，中文原样保存；新文本文件沿用 CRLF，不采用 GBK 解码兜底后静默继续。
- 子进程使用明确可执行入口和参数列表，不把项目名、路径等插入 shell 命令字符串；Windows 启动不弹出额外命令窗口。
- 解析退出码和结构化结果，不用“截取第一个左大括号到最后一个右大括号”作为唯一成功判断。输出无法可靠解析时停止。
- 同一任务中接口分页列表只读取一次；已读取详情按项目/分支/资源 ID 复用。执行前必要的重读不复用旧快照。
- 模型依赖采用引用图，不无限展开；模型只读取一次。写入首版串行，不引入并发写入。
- 全量影响扫描有明确进度和覆盖统计，取消后不把扫描不完整当成检查通过。
- 本地接口只监听回环地址，限制请求来源；写入接口要求本地会话校验，防止其他网页触发操作。
- Markdown/HTML 预览应转义和过滤危险内容；远端描述及示例不能在页面中执行脚本。
- 凭据由 CLI 管理，不读取其令牌文件，不写入计划、日志、分享报告或命令显示区域。
- 本工具拟定性能目标：在固定 1,000 接口/500 模型样例已载入后，本地差异计算 5 秒内完成。目标须实测；网络读取耗时另计并展示进度。

### 12.2 测试方式

- 结构比对、引用和风险规则使用固定输入/输出样例测试，覆盖请求与响应方向差异。
- 原生内容保留、更新语义、超时后核对及分支隔离，必须在专用 Apifox 测试目标中验证，不能只靠本地模拟宣称通过。
- 至少完成一个真实模块的“检查 → 补充 → 预览 → 同步 → 回读 → 再次检查无差异”。
- 正式文档项目的第一次写入，使用已完成审核的小范围任务；不以全量项目作为首次验证样本。
