# Apifox 助手：逐屏观感 critique（十站主工作流）

日期：2026-11-12 写下（第二百零五轮），同日按判断动手两次并回写去向（第二百零五轮 typeset、第二百零六轮 distill）。具名 pass：**critique**（本文件，判断）+ 据判断落地的那几处（文末「本轮落地的 pass」与「第二百零五轮落地的 pass」两节）。

**这份文件是什么**：把主工作流逐屏读一遍，每站回答三件事——现状一句话、像生成物或模板脸的地方在哪（没有就写「没有」）、这一屏在「安静 / 收敛 / 排版」这条线上最该改的一处是哪一处。它不是待办清单的另一种写法：每一站的第三条都点名一个真实存在的文件与控件，改的时候照着找得到东西。

**证据口径**：源码逐屏通读 + `bash .winecheck/demo.sh` 三档报告与讲稿（`/tmp/ah-demo/report-96|120|192.txt` 与 `narration-*.txt`）。写这份 critique 时读的是第二百零四轮那一次的三份报告（208 通过 / 0 失败 ×3）；第二百零五轮复跑读到 217 通过 / 0 失败 ×3，第二百零六轮动手之后再复跑读到 **218 通过 / 0 失败 ×3**、逐屏对账 0 处对不上（差的是第二百轮那九段与本轮那一段提示行行高量测，不是判定变了）。**这些全部是 Linux 容器内 wine 10.0 + Xvfb 模拟器读数，不是 Windows 真机结果**；真机 0 台，G-D5 未达成（环境供给缺口）。凡本文引用一个宽度、一个字宽或一次「放得下」，只有两种来源：wine 报告里那一行的数字，或者源码里的字面常量——**没有第三条路**，因为本环境没有 Windows 图形子系统。真机观感一律随 G-D5 复核，不在本文里宣判。

**十站的出处**：`docs/方案.md` 3.1 首次配置 + 3.2 日常旅程的九步（新建任务 / 源码注释 / 注释应用 / 生成文档 / 响应契约 / Apifox 差异 / 同步预览 / 同步执行 / 报告），一共十站。屏名与 `docs/NOTES.md`「降级答辩脚本」逐屏表同批，序号不同（那张表按证据排，这张按用户走到的顺序排）。

**pass 名册**：`quieter / distill / typeset / layout / clarify / harden / polish`（`docs/方案.md` §6.2 #14）。每站的第三条只点其中一个，不写「优化 UI」这类无法执行的话。

## 第 1 站 · 首次配置（项目设置页与配置对话框）

**现状**：工具栏 + 六列清单 + 右侧详情一张十七行字段网格，四个高级入口（模块与模板 / 序列化与分析 / 模型服务 / 导出配置）收在网格底部同一行；读取失败 → 重试 → 恢复在 wine 三档真走过，行高与「四入口同行」也被量过（`RunProfileFormLayout` 七段，≈100% 档最高行 54px 对阈值 58px）。

**像生成物 / 模板脸**：有，在 `ProjectsPage.cs` 与三个子对话框的说明行落法上。`ProjectsPage.cs` 把一句提示当成「一行的第二格、第一格留空」（`AddRow(grid, "", Ui.Caption("相对路径前缀，用「;」分隔；留空表示只允许导出补丁。"))`），而三个配置子对话框各自带一份私有的 `AddHint`——`ProfileAdvancedDialog.cs`、`GenerationDialog.cs`、`ProfileAnalysisDialog.cs` 里那三份 `AddRow` / `AddHint` 代码逐字相同。同一件事四种写法，读起来就是「没有一处是选过的」那种脚手架感。

**最该改的一处**：收敛（distill）——提示行收成一处工厂，四个文件各留一行调用，文字逐字不动。**第二百零六轮已落地**（去向见文末「本轮落地的 pass」；第二百零五轮那一版判的是「本轮未动」），理由是形状要先定（并进 `Ui.FieldGrid` 还是新建一个 `Ui.HintRow`）；**第二百零六轮按这一处动手，取的形状是 `Ui.HintRow(grid, text)` 新工厂**（配置编辑对话框那种落法——四种写法里唯一在 wine 三档逐行量过行高的一种），三份私有 `AddHint` 删除、`ProjectsPage.cs` 与 `TasksPage.cs` 的空标签调用改经工厂。**动手时才看见的第二件事比原判断值钱**：那三份 `AddHint` 与 `TasksPage.cs` 的 `AddRow` 往标签列放的占位控件是默认尺寸的 `Panel`（200×100），于是每一行提示都被撑到 100px 高——同一个根因 `ProfileFormLayout` 的类注释在第一百四十八轮就写过（配置页那七行 700px 死空白），当时只改了那一个文件，同一族四处没跟上。wine 100% 档改动前后各逐条量过：22 行提示 100px → 25px（三句长提示折两行的 42px，阈值 45px）。**字段行（三份私有 `AddRow`）本轮仍未动**：它们的行内留白取值各不相同，收进同一处会同时改三个对话框的行高，那是另一次 layout，不与这次 distill 混在一处；同名表头列宽（60 / 70 / 110）也仍未动，见文末第 2 条。

## 第 2 站 · 检查任务页

**现状**：七列任务清单 + 右侧九分区详情 + 三阶段进度条 + 唯一「下一步」横幅，都在 `TasksPage.cs` 一屏里；详情区自第三十一轮起可滚动，极端数据在 wine 量过（`RunDetailBreak` 五段：120 字任务名 → 标签 353×232、141 字范围行 → 368×85、334 字错误消息 → 文字 2348px 对状态行 84×29px）。

**像生成物 / 模板脸**：没有。五段分区说明行的句式在第一百五十六轮被刻意打散（问句 / 结果导向 / 陈述 / 条件 / 动作导向，五个收尾各不相同），本轮逐段读下来没有聚回同一个模子；`CaptionBrevityTests.TaskDetailCaptions_DoNotShareOneSentenceShape` 也盯着同一收尾出现三次即红。

**最该改的一处**：布局（layout）——状态行那一格太窄，而这一条是排版线（安静 / 收敛 / 排版）上最值钱的。wine 三档读数：640 到 1280 七档窗口宽度下这一行的宽恒为 194px，一条 94 字的真实失败原因文字是 642px（`RunStatusFullText`），于是「放得下就不给入口」那一支在这一屏几乎永远走不到，用户每一次失败都要多点一次「查看完整错误」。该改的是让这一行按工具栏剩余宽度取宽（与「刷新」和筛选框争同一行，窗口宽了它就宽），而不是把对话框加宽。本轮未动：这一处要动 `ProjectsPage` 与 `TasksPage` 的工具栏布置，属 layout 切片，且改完必须在 wine 重跑那一屏的四段才算有读数。

## 第 5 站 · 生成文档（核对传播与定向构建）

## 第 6 站 · 响应契约

**像生成物 / 模板脸**：有，在 `ContractsDialog.cs` 的「分支」列上——而且这次是一处真正的排版违规，不是口味问题。那一列是每条契约的分支数，此前走控件默认的比例字体；同一只壳里检查结果对话框的数值列是等宽的（`CheckResultsDialog.cs` 的 `AddCount`）。后果不是难看而是可比性：比例字体下「9」与「10」宽度不同，两次扫描之间数字一变整列左右抖，用户没法用余光比较同一列的两个数——§3 与 `docs/功能清单与验收标准.md` 设计验收 D5「比例字体下跳宽即不合规」判的就是这一条。

**最该改的一处**：排版（typeset），本轮已落地：计数格的等宽字体收成唯一落点 `Ui.CountCell`（`Ui.cs`），五处调用一并跟上。同一轮如实记下没做的另一半——标识格（接口身份、远端 ID、Apifox 项目 ID、源码路径）仍是各屏就地设一次，其中 `ContractsDialog.cs` 的首列（接口身份）与 `ProjectsPage.cs` 的「Apifox 项目」ID 列一处都没设，挂账写在 `docs/DESIGN.md` §8「数字等宽」。

## 第 8 站 · 同步预览（勾选与冻结计划）

**现状**：勾选页（接口复选清单 + 「全选可同步（N）」+ 关键词框，勾选状态按接口键记在 `SyncSelect`，筛选与排序都不丢勾选）→ 预览页（概要、指纹、写入清单、写入内容脱敏预览、未纳入清单）；wine 下这一屏有构造与状态行四段读数（`RunDialogStatusSweep`），计划生成与写入门禁走的是用例与服务层证据。

**像生成物 / 模板脸**：有，是一处脚手架残留：`SyncPreviewDialog.cs` 的写入清单第一列表头写的是 `#`（`_actionList.Columns.Add("#", 40)`）——原生界面所有清单表头里唯一一个纯符号。它不是设计选择，是从冻结页面抄来的（页面层按 §2.4 已冻结、只修阻断性缺陷），符号就这样漏进了主交付面，与 §1「中文单语」和 §1「没有一处是选过的」两条都对不上。

**最该改的一处**：文案（clarify）——把「#」改成「序号」。但宽度必须先量：那一列是 40px，而排序的「▲/▼」标记会追加在表头文字之后（`ListSort.Header`），40px 放不放得下「序号▲」在 Linux 判不了（没有 Windows 图形子系统，wine 也没量过这一格），照抄改字有把表头截断成「序…」的风险。所以这一处留到下一轮，先在 wine 量一次这一格的表头宽再改——**这条批评的价值一半在「不要不量就改」**。

**最该改的一处**：收敛（distill）——「一屏两个关键词框时，查找手势交给哪一个」这条判定在三个对话框里各写一次：`SyncPreviewDialog.cs`（勾选页与预览页各一个框）、`ApplyPlanDialog.cs`（文件清单与跳过清单）、`CheckResultsDialog.cs`（接口清单与模型清单）。三处都各自用 `_page1.Visible` 一类条件挑一个框，规则相同（一次按键只有一个落点、Ctrl+F 交给这一屏的主清单），落点在代码里却是三份。该收成一处判定（比如「本屏的主关键词框」由各视图登记一次，手势分发只问它），否则第四个双框视图出现时会写出第四种。本轮未动。

## 第 10 站 · 报告与交接

**现状**：Markdown 源文只读预览（等宽、不折行、双向滚动，与「导出 Markdown」同一份字节）+ 「前端交接说明」实心主按钮 + Markdown / HTML / JSON 三个 ghost，全部经原生另存为导出；预览读取失败时正文区给指引并禁用导出、旁边一颗「重试」。

**最该改的一处**：这一屏判「不动」，但要把缺的读数写清：wine 三档只量过四种格式的真实字节数（`RunFullJourney` 第八段），没量过这块预览框在一百多字的单行下横向滚动是否跟手、也没量过四个导出按钮在同一行的实际宽度。这两条随 G-D5 真机复核，不在本文里宣判，也不该被算成缺陷。
