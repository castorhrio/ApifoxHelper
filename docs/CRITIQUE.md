# Apifox 助手：逐屏观感 critique（十站主工作流）

日期：2026-11-12 写下（第二百零五轮），同日按判断动手两次并回写去向（第二百零五轮 typeset、第二百零六轮 distill）。具名 pass：**critique**（本文件，判断）+ 据判断落地的那几处（文末「本轮落地的 pass」与「第二百零五轮落地的 pass」两节）。

**这份文件是什么**：把主工作流逐屏读一遍，每站回答三件事——现状一句话、像生成物或模板脸的地方在哪（没有就写「没有」）、这一屏在「安静 / 收敛 / 排版」这条线上最该改的一处是哪一处。它不是待办清单的另一种写法：每一站的第三条都点名一个真实存在的文件与控件，改的时候照着找得到东西。

**证据口径**：源码逐屏通读 + `bash .winecheck/demo.sh` 三档报告与讲稿（`/tmp/ah-demo/report-96|120|192.txt` 与 `narration-*.txt`）。写这份 critique 时读的是第二百零四轮那一次的三份报告（208 通过 / 0 失败 ×3）；第二百零五轮复跑读到 217 通过 / 0 失败 ×3，第二百零六轮动手之后再复跑读到 **218 通过 / 0 失败 ×3**、逐屏对账 0 处对不上（差的是第二百轮那九段与本轮那一段提示行行高量测，不是判定变了）。**这些全部是 Linux 容器内 wine 10.0 + Xvfb 模拟器读数，不是 Windows 真机结果**；真机 0 台，G-D5 未达成（环境供给缺口）。凡本文引用一个宽度、一个字宽或一次「放得下」，只有两种来源：wine 报告里那一行的数字，或者源码里的字面常量——**没有第三条路**，因为本环境没有 Windows 图形子系统。真机观感一律随 G-D5 复核，不在本文里宣判。

**十站的出处**：`docs/方案.md` 3.1 首次配置 + 3.2 日常旅程的九步（新建任务 / 源码注释 / 注释应用 / 生成文档 / 响应契约 / Apifox 差异 / 同步预览 / 同步执行 / 报告），一共十站。屏名与 `docs/NOTES.md`「降级答辩脚本」逐屏表同批，序号不同（那张表按证据排，这张按用户走到的顺序排）。

**pass 名册**：`quieter / distill / typeset / layout / clarify / harden / polish`（`docs/方案.md` §6.2 #14）。每站的第三条只点其中一个，不写「优化 UI」这类无法执行的话。

## 第 1 站 · 首次配置（项目设置页与配置对话框）

**现状**：工具栏 + 六列清单 + 右侧详情一张十七行字段网格，四个高级入口（模块与模板 / 序列化与分析 / 模型服务 / 导出配置）收在网格底部同一行；读取失败 → 重试 → 恢复在 wine 三档真走过，行高与「四入口同行」也被量过（`RunProfileFormLayout` 七段，≈100% 档最高行 54px 对阈值 58px）。

**像生成物 / 模板脸**：有，在 `ProjectsPage.cs` 与三个子对话框的说明行落法上。`ProjectsPage.cs` 把一句提示当成「一行的第二格、第一格留空」（`AddRow(grid, "", Ui.Caption("相对路径前缀，用「;」分隔；留空表示只允许导出补丁。"))`），而三个配置子对话框各自带一份私有的 `AddHint`——`ProfileAdvancedDialog.cs`、`GenerationDialog.cs`、`ProfileAnalysisDialog.cs` 里那三份 `AddRow` / `AddHint` 代码逐字相同。同一件事四种写法，读起来就是「没有一处是选过的」那种脚手架感。

**最该改的一处**：收敛（distill）——提示行收成一处工厂，四个文件各留一行调用，文字逐字不动。**第二百零六轮已落地**（去向见文末「本轮落地的 pass」；第二百零五轮那一版判的是「本轮未动」），理由是形状要先定（并进 `Ui.FieldGrid` 还是新建一个 `Ui.HintRow`）；**第二百零六轮按这一处动手，取的形状是 `Ui.HintRow(grid, text)` 新工厂**（配置编辑对话框那种落法——四种写法里唯一在 wine 三档逐行量过行高的一种），三份私有 `AddHint` 删除、`ProjectsPage.cs` 与 `TasksPage.cs` 的空标签调用改经工厂。**动手时才看见的第二件事比原判断值钱**：那三份 `AddHint` 与 `TasksPage.cs` 的 `AddRow` 往标签列放的占位控件是默认尺寸的 `Panel`（200×100），于是每一行提示都被撑到 100px 高——同一个根因 `ProfileFormLayout` 的类注释在第一百四十八轮就写过（配置页那七行 700px 死空白），当时只改了那一个文件，同一族四处没跟上。wine 100% 档改动前后各逐条量过：22 行提示 100px → 25px（三句长提示折两行的 42px，阈值 45px）。**字段行（三份私有 `AddRow`）仍未动**：它们的行内留白取值各不相同，收进同一处会同时改三个对话框的行高，那是另一次 layout，不与这次 distill 混在一处；**同名表头列宽（60 / 70 / 110）第二百四十二轮已收成一处**（先量再改，读数与代价见文末「第二百四十二轮落地的 pass」）。

## 第 10 站 · 报告与交接

## 第二百四十四轮落地的 pass（harden + clarify，还是第 8 站那一屏）

- **先量到的一件比简报硬**：上一轮末尾补的那两条门（窗体高等于算式在实测那一格的取值、行数改了算式跟着改）**实测是空的**。跑法：把 `DialogHeightFor` 整个改回 `=>` 字面量 790，`SyncPreviewPanesTests` 十条**照样全绿**。成因不是断言写错，是判点选错——那两条都只取「算式在 8 行那一点的取值」，而那一点上算出来的 790 与写死的 790 是同一个数，门没有能把它们分开的判据。简报要的「常量与判据脱钩」这一形状确实在，但它给的切片（再补两条同判点的断言）补不住这一发。
